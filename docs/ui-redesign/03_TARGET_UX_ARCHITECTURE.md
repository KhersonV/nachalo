# UI Stage A — целевая UX и компонентная архитектура

Это проект для Stage B+, без реализации. Исходный реестр — [01_FUNCTIONAL_INVENTORY.md](01_FUNCTIONAL_INVENTORY.md), подтверждённые связи — [02_ARCHITECTURE_AUDIT.md](02_ARCHITECTURE_AUDIT.md).

## Навигация и информационная архитектура

Постоянная навигация Lobby содержит ровно **Profile, History, Shop, Base, Inventory, Modes**. Текущий URL `/equipment` можно сохранить под названием Inventory; `/game` — отдельный полноэкранный режим с HUD, без седьмой вкладки Battle. `/login`, `/register`, служебные лаборатории и `/game/stats` не входят в Lobby navigation.

| Раздел | Владелец сценария | Соседний контекст, который остаётся доступным |
|---|---|---|
| Profile | Аккаунт, ник/аватар, уровень/XP, статус, поиск, друзья и заявки | Краткая сводка баланса и прогресса остаётся; текущая общая/классовая статистика Profile должна быть доступна через History после переноса, без удаления во время перехода. |
| History | Список и подробности завершённых матчей, личные итоги, награды, общая/классовая статистика по мере подтверждения API | Текущий результат матча открывается из HUD; история — устойчивый просмотр после выхода. Не рисовать несуществующие фильтры как работающие. |
| Shop | Покупка расходников/свитков/чертежей, количество/цена, продажа неэкипированного gear | Зелёные комплекты явно «скоро», пока API покупки нет. Баланс выводить из профиля/ответа сервера. |
| Base | Forge/Library/Tavern, уровни, затраты ресурсов, наём и активация героев | Рецепты Forge и исследования Library показывать как информацию до появления реального действия. Read-only loadout допустим, но редактирование — в Modes. |
| Inventory | Выбор героя **для просмотра**, слоты, экипировка, сравнение характеристик, set bonuses, постоянный склад | Активация героя остаётся в Base; при желании дать прямую ссылку «Сделать активным» в Base, не путать с локальным выбором. |
| Modes | Режим, состав party, приглашения, активный герой, редактирование loadout, очередь, отмена и готовность | Друзья здесь нужны для приглашения; управление дружбой остаётся в Profile. |
| HEX HUD | Поле, HP/энергия, ход/таймер, цель/действие, рюкзак, строительство, события, присутствие, результат | Сервер определяет доступность действий, геометрию, туман, урон, стоимость, награды. |

Порядок внимания на каждом экране: **основное действие → необходимое состояние/ограничение → подробности**. Скрывать редкие детали за раскрытием, сохраняя все действия F01–F85. Успех, ошибка, пусто и загрузка имеют постоянные места, не перекрывают критические кнопки.

## Компоненты с понятными границами

| Уровень | Компоненты | Состояние и запросы |
|---|---|---|
| Общая оболочка | `AppShell` для Lobby, `LobbyNavigation` (на основе `LobbyHeader`), `PageHeader`, `StatusBanner`, `EmptyState`, `LoadingState`, `ConfirmDialog`, `NotificationCenter` | Никаких экономических расчётов. `AppShell` не подписывается на WS/SSE повторно; глобальную подписку оставить единственной в layout. |
| Общие данные, разные сценарии | `ResourceSummary`, `HeroCard`, `StatsSummary`, `StatComparison`, `MatchResultSummary`, `ItemCard` как визуальный примитив | Получают нормализованные props. Shop/Equipment/Match Backpack имеют разные action wrappers и DTO. |
| Profile | `AccountSummary`, `ProfileEditor`, `PlayerSearch`, `FriendCard`, `FriendRequestList` | Контейнер Profile владеет API G Profile/Friends; локальные формы и relation. |
| History | `MatchHistoryItem`, `MatchDetail`, `RewardList` | Контейнер History владеет G history; детали не перечитывают текущий live match. |
| Shop | `ShopCategoryTabs`, `ShopItemCard`, `QuantityControl`, `SellItemCard` | Контейнер Shop владеет каталогом/покупкой/продажей; `POST` отдельно от презентации. |
| Base | `BuildingPanel`, `BuildingCost`, `HeroRoster`, `TavernHeroAction` | Контейнер Base владеет G base/heroes и обновлением после строительства/найма. |
| Inventory | `HeroSelector`, `EquipmentSlot`, `EquipmentItemCard`, `SetBonusCard` | Контейнер Equipment владеет `/game/equipment`; выбор героя для просмотра не пишет active hero. |
| Modes | `ModeCard`, `PartyPanel`, `PartyInviteCard`, `QueueStatus`, `MatchReadyModal`, `StorageLoadout` | Один координатор перехода к матчу принимает события M от глобального listener и состояния Modes; без параллельных redirect timer. |
| Game HUD | `GamePanel`, `TurnClock`, `PlayerVitals`, `TargetPanel`, `MatchBackpack`, `CombatEventList`, `GameNotification`, `GameResultShell` | Контейнер режима переводит серверный snapshot/patch в props. Кнопки вызывают intents; расчёты на сервере. |

Это набор крупных повторяемых блоков, не предложение дробить каждую подпись или иконку в отдельный компонент. Текущие `ActionLog`, `HexMatchResults`, `PlayerHUD`, `StorageLoadout`, `MatchReadyModal` можно адаптировать, если сохранить их сценарные контракты.

## Где живёт состояние

| Состояние | Источник истины | Клиентский слой |
|---|---|---|
| Сессия/user ID | A JWT + G/M авторизация | `AuthContext`; `localStorage` только для восстановления сессии. |
| Герой, экипировка, баланс, база, друзья | G/PostgreSQL | Серверные ответы; локальный cache на странице или тонкий общий query layer, инвалидируемый после мутаций. Текущий Redux для Lobby не обязателен. |
| Party, очередь, созданный матч | M | SSE + `currentMatch` fallback; один координирующий state machine для перехода. |
| Square матч | G snapshot/WS и revisions | Существующий Redux `gameSlice`/`combatPresentationSlice`; сохранять `createWsHandlers` до проверки. |
| HEX матч | G персональный snapshot/WS и revisions | `useHexMatchSnapshot`; локально только UI selection, открытые панели и playback. |
| Таймер, туман, урон, награды, инвентарь матча | G/PostgreSQL | Отображение серверного deadline/result; клиент не создаёт альтернативную формулу. |
| Тема/вкладка/сортировка/фокус/диалог | Клиент | Локальный React state; persistence лишь где текущий UX требует (например, suppression модалки). |

Следующий шаг для данных Lobby — маленькие функции API по доменам (`profile`, `friends`, `heroes`, `shop`, `equipment`, `base`, `history`, `matchmaking`) и согласованная загрузка/инвалидация. Не менять URL или backend API в первом UI этапе. Общие визуальные компоненты получают уже нормализованные типы; адаптеры DTO располагаются рядом с feature, не внутри карточек.

## Готовность к 3D HEX

Разделить **match controller**, **field renderer** и **HUD**. Контроллер предоставляет `{snapshot, selectedCell, selectedTarget, allowedActions, dispatchIntent, visualEvents}`. Поле получает axial q/r, видимые клетки/объекты и callbacks `onCellSelect/onActorSelect`, ничего не знает о fetch, цене или наградах. HUD использует те же данные в 2D и 3D. `HexMap` можно заменить сценой, сохранив `HexGameController`/его будущий controller hook, `Inventory`, `TurnClock`, `TargetPanel`, `CombatEventList`, `HexMatchResults`. `LiveMatchScene3D` Square — полезный опыт презентации, но не готовый HEX renderer. Окончательный движок Stage A не выбирает.

Фильтр видимости должен остаться на сервере; UI не должен отправлять чужие координаты через общие уведомления. `commandId` и revision gate защищают повторные команды и порядок patch. Боевые индикаторы и анимации читают visual events, не управляют исходом действий. Ввод мышью/тачем/клавиатурой переводится в одинаковые intents.

## Дизайн-система: исходные токены

Рекомендации для проверки контраста и экранов в Stage B, **не CSS-код**. Цвета: `canvas #0B111B`, `surface #121B29`, `surfaceRaised #1C2938`, `border #344356`, `text #F2F0E8`, `textMuted #B3C0CE`, `gold #D7B46A` для декоративного/наград, `action #6BB9E8` для интерактивного, `success #79C99A`, `warning #E2AE5D`, `danger #E47D83`, `focus #9CD6FF`. Проверить WCAG контраст на реальных состояниях; не использовать золото для единственного указания действия.

| Примитив | Предлагаемый контракт |
|---|---|
| Типографика | UI sans для текста, декоративный serif только для крупных заголовков; 14/16/20/28/36 px, line-height 1.35–1.55; табличные числа для таймера, цены, HP. |
| Spacing | Шкала 4/8/12/16/24/32/48 px; в карточке 12–16, между секциями 24–32. |
| Радиусы/границы/тени | Радиусы 6/10/14 px; граница 1 px, тень мягкая и редкая; декоративные уголки не мешают hit area. |
| Карточки и сетка | Минимальная ширина карточки предмета 240 px, героя/режима 280 px; desktop 12 колонок, tablet 6, mobile 4, без горизонтального скролла основных действий. |
| Кнопки | Primary только основное действие, secondary для навигации/подтверждения, danger для удаления; min-height 40–44 px, visible focus, disabled с текстовой причиной. |
| Поля/вкладки | Явные label, ошибки у поля, клавиатурная навигация; вкладки сохраняют контекст/счётчик, выбранное состояние не кодируется только цветом. |
| Диалоги/tooltip | ConfirmDialog для трат/продажи/опасных действий; фокус внутри и возврат; tooltip дополняет, не заменяет текст. `MatchReadyModal` показывает countdown и явный выход. |
| Уведомления/статусы | Три приоритета: блокирующая ошибка, временное событие, тихое обновление; источник и причина указаны словами. Игровой HUD держит важные события в доступном журнале. |
| Пусто/загрузка/ошибка | У каждого раздела конкретный empty copy и действие, skeleton сохраняет геометрию, retry вызывается явно; не заменять серверную ошибку общим «не работает». |
| Адаптивность | Mobile: одна колонка, фиксированная зона главного действия и читаемый HUD; desktop: основная область + контекстная панель. Поддержать reduced motion. |

Визуальный язык: тёмно-синие и графитовые поверхности, золотой акцент для статуса/награды, голубой для действия, умеренная dark fantasy декорация. Текст, границы и состояния должны оставаться читаемыми без анимации и 3D.
