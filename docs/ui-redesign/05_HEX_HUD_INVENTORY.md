# Stage I.1 — инвентаризация HEX HUD

Проверено по текущему коду `src/app/game/page.tsx`, `src/features/game/GameWrapper.tsx`, `src/components/HexGameController.tsx`, `HexMap.tsx`, `Inventory.tsx`, `PlayerHUD.tsx`, `ActionLog.tsx`, `HexMatchResults.tsx`, `src/hooks/useHexMatchSnapshot.ts`, `src/types/HexGameTypes.ts` и обработчикам `beckend/gameservice/handlers/hex_*.go`. Stage A: `01_FUNCTIONAL_INVENTORY.md` (F63–F77), `02_ARCHITECTURE_AUDIT.md`, `03_TARGET_UX_ARCHITECTURE.md`, `04_IMPLEMENTATION_ROADMAP.md`. Это инвентаризация существующего поведения, не контракт новых возможностей.

## Вход и источники состояния

`/game?instance_id=…` монтирует `GameWrapper`. Он сначала запрашивает Square `/game/match`; HTTP 409 переключает на персональный `GET /game/hex/{id}` (или `/game/hex-test/{id}` для лаборатории). `HexGameController` получает initial snapshot и `useHexMatchSnapshot` поддерживает его HTTP/WS. Redux Square не является хранилищем HEX. Герой в бою — `snapshot.player`, выбранный при подготовке в Lobby; выбора/смены героя внутри HEX нет. Это необходимо сохранить: изменение героя посреди боя не предусмотрено.

Ниже «snapshot» означает `HexSnapshot` схемы 2, полученный для конкретного пользователя; `route`, `attackPreview`, выбранная клетка/цель и журнал — только временное состояние интерфейса. Все POST идут по `/game/{hex|hex-test}/{instanceId}/…` с bearer token. Там, где указано `commandId`, текущий контроллер хранит его в `pending*` ref для повторной попытки и сериализует действия через `actionInFlight`/`busy`.

## Режимы и классы

Lobby предлагает `PVE`, `1x1`, `1x2`, `2x2`, `3x3`, `5x5` (`ModeSelectionPage.tsx`). HEX HUD сейчас не строит отдельные варианты по mode: использует `snapshot.mode`, `teamId`, `activeUser`, `turnOrder` и персональный `actors`. Поэтому будущий состав команды надо строить по фактическому snapshot, а не по фиксированному числу слотов. В PvE также возможны монстры; в PvP цель бывает `player` и `monster` только когда таков filtered snapshot. Режим `hex-test` — отдельный лабораторный путь, портал в нём недоступен.

`guardian`, `ranger`, `berserker`, `mystic` существуют в серверном каталоге (`handlers/heroes.go`). В HEX `characterType/isRanged/attackRange` и реальные HP/Energy приходят с сервера. Серверные `handlers/hex_combat.go`, `hex_pvp.go` реализуют классовые пассивные эффекты и последовательность удара: Guardian response/aura, Ranger ranged/crit/refund, Berserker lifesteal/follow-up/counter reduction, Mystic penetration/эффекты. `repository/hex_guardian_aura.go` влияет на движение. Точные условия, вероятность и стоимость не следует переносить в HUD. `HexAttackResult.effects/steps` и visual notice содержат подтверждённые эффекты; отдельного списка активных эффектов, ability IDs, cooldowns или команды «использовать способность» в `HexSnapshot`/текущем HUD нет. Для Stage I.2 допустима информационная секция о классе/подтверждённых эффектах, но активные ability slots без серверного контракта должны оставаться отсутствующими, а не выглядеть работающими.

## Reconnect, revisions и Fog of War

`useHexMatchSnapshot` валидирует schema 2 и `instanceId`, хранит последний snapshot и `stateRevision` ref. После WS open отправляет `JOIN_MATCH` и вызывает HTTP refresh; после close переподключается через 1500 мс. `MATCH_UPDATE` принимается при ревизии не ниже текущей; новый `MATCH_PATCH` запускает refresh. `MATCH_HEX_VISUAL` применяется как временная презентация, не как источник HP/позиции. HTTP 404/410 отмечает матч недоступным. SSE `GlobalMatchListener` относится к matchmaking/входу в матч, не заменяет HEX WS. В текущем hook нет отдельного публичного состояния `connecting/reconnecting`; для Stage I.2 его потребуется вывести из той же подписки, сохранив её единственной.

Backend `repository/hex_match.go:filterHexSnapshotTx` удаляет скрытые ресурсы, бочки, структуры, actors, edges и координаты quest/portal согласно видимости команды. HUD и renderer должны читать только этот DTO, не seed, глобальные каталоги или чужие данные. Особый риск текущего контроллера: локально сохранённые `selectedCell`, `target` и `route` могут пережить изменение видимости, если их не перепроверить при новой ревизии; при миграции нужно закрывать недействительный контекст, не показывая устаревшие сведения.

## Сверка с прежним HUD

`HexGameController` содержит все действия F63–F77 из Stage A: route/move, preview/attack, structure, collect/barrel, use-item/build, end-turn, extract, notices, result. `PlayerHUD`, `Inventory`, `ActionLog` переиспользуются со Square, но HEX использует их через отдельные props/колбэки. Автономной HEX панели активных способностей и quick slots сейчас нет. Это зафиксированное отсутствие, а не основание удалить классовые эффекты или существующую кнопку инвентаря в Stage I.2.
