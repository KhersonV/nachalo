# Первый HEX-прототип

Есть два режима: read-only генератор без базы и отдельный тестовый игровой матч с движением через PostgreSQL. Обычный matchmaking по-прежнему создаёт только square-матчи. Оба HEX snapshot используют `schemaVersion: 2`, `geometry: hex-v1` и позиции `{q,r}`; JSON можно скачать в браузере.

## Запуск без базы данных

В двух терминалах из корня проекта:

```sh
cd beckend/gameservice && go run ./cmd/hex-preview
```

```sh
NEXT_PUBLIC_API_BASE=http://127.0.0.1:18081 npm run dev
```

Открыть <http://localhost:3000/hex-lab>. Seed меняет воспроизводимую карту; клик по клетке показывает `(q,r)` и terrain. `GET http://127.0.0.1:18081/game/hex-preview?seed=1` возвращает тот же JSON. В обычном GameService этот read-only маршрут доступен только при `HEX_PREVIEW_ENABLED=true`.

Генератор строит конечный HEX-диск, комнаты, соединяющее дерево коридоров, непроходимый камень и стены на границах пола с камнем. В режиме предпросмотра маркеры игрока и монстров служат только для проверки проекции.

## Тестовый игровой матч

Нужны локальная **отдельная тестовая** PostgreSQL, применённые вручную `stage1_geometry.sql` и `stage2_commands.sql`, действующий JWT аккаунта с выбранным героем в этой тестовой базе. Никогда не направляйте следующие команды на пользовательскую БД.

После создания пустой локальной БД с именем, содержащим `test`, из корня проекта:

```sh
export HEX_TEST_DB_DSN='postgres://USER@127.0.0.1:PORT/nachalo_hex_test?sslmode=disable'
cd beckend/gameservice && go run ./cmd/hex-test-schema
cd ../..
psql "$HEX_TEST_DB_DSN" -v ON_ERROR_STOP=1 -f docs/hex-migration/stage1_geometry.sql
psql "$HEX_TEST_DB_DSN" -v ON_ERROR_STOP=1 -f docs/hex-migration/stage2_commands.sql
psql "$HEX_TEST_DB_DSN" -v ON_ERROR_STOP=1 -f docs/hex-migration/stage3_hex_pve.sql
```

Запустить GameService с `GAME_DB_DSN=$HEX_TEST_DB_DSN`, `HEX_TEST_MATCH_ENABLED=true`, `HEX_PREVIEW_ENABLED=true` и обычным тестовым `JWT_SECRET_KEY`. Из корня проекта запустить frontend с `NEXT_PUBLIC_API_BASE=http://127.0.0.1:8001`, `NEXT_PUBLIC_WS_URL=ws://127.0.0.1:8001/ws` и адресами локальных тестовых auth/matchmaking сервисов. Войдите в тестовый аккаунт, у которого есть профиль и выбранный герой в этой GameService БД, откройте `/hex-lab` и нажмите «Создать игровой HEX-матч». URL получит `?match=hex-test-…` и после обновления страницы загрузит матч из PostgreSQL.

Первый клик по HEX-клетке запрашивает серверный маршрут, показывает число шагов и стоимость. Второй клик по той же клетке подтверждает команду с `commandId`. Сервер повторно проверяет очередь, маршрут и энергию внутри `MatchCommand`; сохранение позиции, энергии и занятости клеток, ledger и revisions проходит одним commit. `MATCH_PATCH` отправляется после commit. Повтор команды возвращает прежний результат без повторной рассылки.

Тестовый матч однопользовательский. В нём используются существующие профиль, выбранный герой, эффективные характеристики экипировки, каталоги монстров и ресурсов, таблицы матчей, инвентаря и очереди ходов. На карте появляются три обычных ресурса из каталога. Выберите клетку с ромбом и нажмите «Подобрать». Как и square `ApplyResourceCollection`, команда требует активного живого игрока и существующего ресурса, но не добавляет проверку дистанции. Подбор клетки, JSON-инвентаря, `inventory_items`, ledger и revisions проходит в одном `MatchCommand`; повтор `commandId` возвращает исходный результат. После commit HEX Lab обновляет snapshot.

Кнопка «Завершить ход» передаёт ожидаемый номер раунда. Однопользовательская очередь переходит к тому же игроку и следующему раунду, восстанавливая энергию по существующему шаблону класса. HTTP и 60-секундный таймер вызывают один `ApplyHexEndTurn` под блокировкой матча: просроченный таймер отклоняется, состояние и событие сохраняются после одного commit. Ресурсы не тратят энергию. Изменения карты повышают `mapRevision`; завершение хода повышает только `stateRevision`. Для тестового формата команда явно отклоняет введённые извне постройки, бочки, портал и quest artifact, потому что их эффекты ещё не перенесены. После рестарта таймер запускается снова при загрузке HEX snapshot; исходный deadline пока не хранится в PostgreSQL.

HEX Lab позволяет выбрать монстра. Первый клик запрашивает `/attack-preview` и показывает HEX-дистанцию, режим и цену энергии; второй клик по тому же monster ID либо кнопка «Атаковать» отправляет `/attack` с `commandId`. Сервер повторяет проверку под `MatchCommand` после блокировки строки матча. Дальность считается из `(q,r)`, для ближней атаки нужна соседняя клетка, а line of sight проверяет пересечение центра луча со стенами и непроходимым камнем. Положение и цену из клиента сервер не принимает. HP и результаты обмена отображаются после commit; `MATCH_PATCH` служит сигналом загрузить новый snapshot. Старые square `/move`, `/attack`, `/collectResource` и `/endTurn` явно отклоняют `hex-test`.

HEX PvE использует исходные чистые функции `applyDamage`, `applyFlatDamage`, `tryApplyRangerCriticalShot`, `resolveAttackEnergyCost`, `resolvePresentationAttackStyle` и те же константы/порядок из square combat. Для поддерживаемых веток HP/энергия, контратака, смерть монстра, существующий equipment drop, `combat_result_events`, ledger и revisions сохраняются одной транзакцией. Дроп экипировки по действующему правилу сразу выдаётся владельцу через `item_instances`; это не предмет на клетке для подбора. `mapRevision` растёт при удалении монстра, `stateRevision` — один раз за атаку. PvP в однопользовательском формате отсутствует.

| Класс | Поддерживаемые HEX PvE-ветки | PostgreSQL integration | Пока отклоняется |
| --- | --- | --- | --- |
| Guardian | Ближний удар, контратака монстра, Guardian response, смерть монстра и дроп | Да: ответный урон, смерть/дроп, replay/rollback, смертельная контратака | Aura против игроков в этом формате неприменима |
| Mystic | Ближний и дальний удар, прежнее снижение защиты монстра до 60%, ближняя контратака | Да: оба режима и формула урона | Quest artifact эффекты; матч их явно запрещает |
| Berserker | Ближний удар, lifesteal, уменьшение контратаки до 55%, дополнительный удар | Да: все перечисленные эффекты с принудительным RNG в тесте | PvP механики вне однопользовательского формата |
| Ranger | Ближний и дальний удар, critical shot, Armor Break, третий выстрел с возвратом энергии, Push или fallback damage | Да: крит, стеки, третий выстрел, успешный Push, заблокированный Push, replay | PvP механики вне однопользовательского формата |

Armor Break хранится в `match_monsters.hex_armor_break_stacks` и `hex_armor_break_turns`, а не только в памяти процесса. На каждом завершённом HEX ходе срок уменьшается; на третьем попавшем дальнем выстреле стеки сбрасываются. Порядок прежний: основной урон с текущим штрафом защиты, затем critical shot, затем эффект третьего выстрела. Push выбирает ближайшее направление axial HEX к лучу атаки, проверяет границы карты, камень, стены и занятость; координаты монстра и revisions сохраняются в одном `MatchCommand`. При невозможном Push действует прежний дополнительный урон в половину рассчитанного урона с прежним минимальным значением.

Смертельная контратака и внутренняя атака монстра используют тот же ledger и транзакцию, что и урон, HP, энергия, события результатов, очередь и клетка. `ApplyHexMonsterAttack` — только внутренняя серверная функция, отдельного HTTP маршрута от имени монстра нет. Повтор `commandId` возвращает сохранённый результат без второго урона и без повторной публикации. Если погибает единственный игрок, тестовый матч получает `active_user_id=0`, `turn_order=[]`, свободную клетку и `finished_at` в том же commit. Его `combat_results_complete=false`, поэтому награды не начисляются и отдельная legacy финализация не запускается. Такой завершённый матч остаётся доступен для replay по ledger, но обычный HEX snapshot не загружается как живой матч.

Ограничения: обычный matchmaking не создаёт HEX матчи; PvP, турели, бочки, портал и quest artifact не реализованы для HEX. Нет автоматического планировщика атак монстров: внутренняя функция выполняет переданную сервером команду, но тестовый ход сам её не вызывает. Не сохранён deadline таймера между перезапусками, нет серверной фильтрации видимости и полной наградной финализации тестового матча. До этих работ режим остаётся за флагом `HEX_TEST_MATCH_ENABLED`; полным PvE его объявлять нельзя.

## Проверка в браузере на изолированной PostgreSQL (19.10.2026)

Headless Chrome открыл `/hex-lab` с локальным тестовым GameService и отдельной PostgreSQL на `127.0.0.1:55433`; профиль и JWT относились только к этой БД. Через элементы интерфейса созданы `hex-test` матч и маршрут, выполнен второй клик для движения, подобран `food`, завершён ход, дождались реального 60-секундного таймера, дважды обновили страницу и подобран `water`. Подбор `water` сначала принудительно откатили тестовым PostgreSQL trigger на `inventory_items`, затем повторили той же кнопкой после снятия trigger. Состояние после ошибки сохранило ресурс и прежние revisions; повторное нажатие использовало тот же `commandId` и выдало одну единицу предмета. На экране после двух подборов видны `food ×1, water ×1`. Тестовый trigger удалён.

| Проверка | Через HEX Lab | Через HTTP/SQL |
| --- | --- | --- |
| Создание, движение, цена энергии, подбор, инвентарь, ручной ход/regen, таймер, reload | Да, фактические клики и обновление страницы | Сверено со snapshot и строками PostgreSQL |
| Повтор шага, подбора и хода с тем же `commandId`; другой payload с тем же ID | Нет отдельной кнопки replay | Все три повторных POST не изменили revisions/инвентарь; конфликт вернул HTTP 409 |
| Rollback посередине подбора и повтор той же попытки | Ошибка и успешное повторное нажатие видны в UI | Trigger на записи инвентаря; после ошибки карта, предметы и revisions неизменны; после повтора одна запись ledger |
| Несколько backend-процессов, доставка WS при сбое процесса, срок таймера после рестарта backend | Нет | Нужны durable outbox и сохранённый deadline; текущий UI восстанавливает snapshot после reconnect/reload |

В этой проверке матч прошёл последовательность revisions `1/1 → 2/2` (движение) `→ 3/3` (подбор) `→ 4/3` (ручной ход) `→ 5/3` (таймер) `→ 6/4` (второй подбор). Здесь запись означает `stateRevision/mapRevision`. Следующий таймер закономерно перевёл его в `7/4`. Начальный браузерный тест нажал «Создать» до завершения React hydration и не запустил действие; после ожидания активной кнопки вся цепочка прошла. Это была ошибка тестового сценария, не ошибка игрового обработчика.

## HEX PvE-проверка (19.10.2026)

В отдельной PostgreSQL реальные integration-тесты `TestHexPvEClassesAndDeathPostgres`, `TestHexPvEBlockingRaceAndRollbackPostgres`, `TestHexRangerThirdShotPostgres` и `TestHexPlayerDeathAndInternalMonsterPostgres` проверили четыре класса в поддерживаемых режимах, стены и камень, отрицательные координаты, контратаку и классовые эффекты, конкурентное убийство одной цели, rollback на записи дропа и смерти без WebSocket callback, replay/conflict `commandId`, новые DB-сессии для HP и `DamageEvents`, одну запись `KillEvents` и один equipment item после смерти. Pure geometry `TestVisibleHexWallsRockAndNegativeCoordinates` проверяет симметрию LOS и блокировки.

Headless Chrome прошёл UI-цепочку «создать матч → пройти к Goblin → три ближние атаки → смерть Goblin и сообщение об equipment drop → подобрать обычный ресурс → завершить ход → reload». В БД после неё: один выданный equipment item, шесть `DamageEvents`, один `KillEvent`, `stateRevision/mapRevision=7/4`, раунд 2. Шанс equipment drop в этом **тестовом backend-процессе** выставлялся в 100% существующим `EQUIPMENT_DROP_CHANCE_OVERRIDE`; production значение не менялось. Отдельного «подбора» equipment drop нет по действующему правилу: после смерти он уже принадлежит игроку. UI-подбор в цепочке относится к обычному ресурсу.

## Подтверждённые PvE-ветки (отдельная PostgreSQL, 19.10.2026)

- Guardian: ближний удар, ответ монстра, Guardian response, убийство монстра с equipment drop, смертельная контратака и смерть единственного игрока.
- Mystic: ближний и дальний удар по монстру со снижением его защиты до 60%; ответ монстра в ближнем бою.
- Berserker: ближний удар, lifesteal, снижение урона контратаки до 55%, дополнительный удар после контратаки.
- Ranger: ближний critical shot; дальний выстрел, крит до Armor Break, два сохранённых стека и их истечение по ходам, третий выстрел с возвратом энергии, успешный Push с изменением двух клеток и fallback damage при камне, стене или занятой клетке.
- Внутренняя атака монстра: обычный урон, контратака игрока, смерть игрока, replay без повторного урона; проверен rollback без публикации WS. Для команд игрока проверены replay, конфликт ID, конкурентное убийство, rollback дропа и смерти, сохранённые события и revisions.

Headless Chrome также проверил действующий HEX Lab с имитированными HTTP ответами: три дальних клика Ranger, отображение `armorBreak` и `push`, движение двойным кликом, подбор ресурса и завершение хода. Это проверка браузерного интерфейса; серверные исходы Ranger и смерти подтверждены отдельными тестами на реальной PostgreSQL. Новые сценарии браузера не были повторены сквозным тестом с настоящим backend и БД.
