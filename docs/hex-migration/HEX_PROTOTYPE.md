# Первый HEX-прототип

## Stage 5: исправление атаки и отображения результатов

Обычная HEX-атака после Stage 5 ошибочно отвечала `HEX test match unavailable`: `readHexAttackTx` проверял `matches.quest_artifact_id` и отвергал ненулевое значение, хотя новые обычные матчи намеренно выбирают квестовый артефакт. Убрана только эта устаревшая проверка; `/game` продолжает отправлять `attack-preview` и `attack` с `targetId` и `commandId` в прежние HEX `MatchCommand`. Формулы, очередь, энергия, классовые эффекты, Push, контратака, ledger и посткоммитная WS-рассылка не менялись.

HEX snapshot теперь содержит публичные данные квеста: каталожные название, изображение и описание, статус (не найден, у носителя, на земле, эвакуирован) и объявленные по правилам квеста имя и координаты носителя либо координаты выпадения. `/game` показывает постоянную карточку цели и заметное временное уведомление `QUEST_ARTIFACT_FOUND`; статус восстанавливается из PostgreSQL после reload и меняется при новом snapshot. Другой инвентарь игроков не раскрывается. Текст карточки, статуса и уведомления доступен на en/ru/de.

Результат HEX использует общую оболочку и стили Square-экрана результатов. Сохранённый `hex_player_results.result` дополнен достоверными счётчиками из `combat_result_events` (убийства, нанесённый/полученный урон), номером хода, каталожными названиями и изображениями добычи и снаряжения. При смерти счётчики записываются только когда история боевых событий помечена полной; старые неполные результаты не дополняются вымышленными данными. Доступны способ выхода, золото, XP, перенесённая/потерянная добыча и сохранённая надетая экипировка. Длительность по часам не сохраняется в HEX-результате; PvP-убийств пока нет, поскольку HEX PvP ещё не реализован. `Play Again` открывает обычное меню matchmaking с выбранным прежним режимом для проверки героя и Loadout; `Return to Menu` ведёт в базу. Legacy Square finalizer не вызывается, общая Square-история матчей по-прежнему не наполняется этим HEX-путём. Новая SQL-миграция для этих изменений не требуется: поля результата добавлены в существующий JSONB, а столбцы квеста созданы ранее в Stage 5.

Проверки в этом задании ограничены форматированием Go, целевой компиляцией/unit-тестами без PostgreSQL, TypeScript и `git diff --check`. Пользователю следует вручную проверить обычную атаку и Ranger Push, уведомление всем участникам, смерть/выпадение/повторный подбор, оба способа выхода, экран результата и reload. Docker, PostgreSQL, браузер и production build здесь не запускались.

## Stage 5: квестовый артефакт, портал и результат

Новый HEX-матч выбирает один артефакт из каталога в той же транзакции, что создаёт карту и игроков; его ID сохраняется в `matches.quest_artifact_id` и snapshot. HEX-бочка использует прежний `OpenBarbel()` с прежними шансами и уроном. Если до последней бочки квестовый артефакт не выпал, она выдаёт именно его по правилу Square. Флаг `matches.hex_quest_spawned` фиксируется с открытием бочки в одном `MatchCommand`; после первого выпадения этот артефакт исключён из каталога дальнейших бросков. Повтор `commandId` возвращает ledger response без второй выдачи. После commit событие `QUEST_ARTIFACT_FOUND` входит в `MATCH_PATCH` для участников с ID носителя и HEX-координатами. Текущий `/game` показывает это сообщение на en/ru/de и предмет в общем `Inventory`.

При смертельной контратаке, внутренней атаке монстра или уроне бочки квестовый артефакт выпадает на клетку смерти либо ближайшую доступную по проходам HEX-клетку, если там уже ресурс или бочка. Подбор с той же клетки снова использует транзакционный HEX `collect`. Обычный рюкзак матча и непереодетые находки снаряжения удаляются в транзакции смерти. Постоянный Storage, баланс и надетое снаряжение не изменяются. Одиночный матч завершается с Defeat; смерть одного игрока в общем матче удаляет только его из очереди. До ручной проверки на PostgreSQL эти ветки считаются **реализованными в коде, но не подтверждёнными игровым тестом**.

Нужны ручные миграции `stage5_quest_artifact.sql` и `stage5_portal_extraction.sql` после Stage 4; агент их не применял. Из корня проекта для выбранной пользователем БД: `psql "$GAME_DB_DSN" -v ON_ERROR_STOP=1 -f docs/hex-migration/stage5_quest_artifact.sql`, затем `psql "$GAME_DB_DSN" -v ON_ERROR_STOP=1 -f docs/hex-migration/stage5_portal_extraction.sql`. Старые HEX-матчи с `quest_artifact_id=0` продолжают играть, но новая эвакуация требует `hex_reward_events_ready=true`, которое устанавливается только для новых матчей с полной транзакционной записью событий.

Обычный HEX-матч (`/game`, не `hex-test`) позволяет выйти только стоя на портале в свой ход. Если у героя есть именно `matches.quest_artifact_id`, сервер разрешает только бесплатный способ; иначе требуется подтверждённая платная эвакуация и минимум 50 золота на постоянном профиле. UI показывает баланс и кнопку по фактическому snapshot. При выходе `MatchCommand` под блокировкой строки матча и профиля переносит рюкзак в существующий Storage суммированием количества, исключает квестовый артефакт, делает найденное снаряжение постоянным, удаляет предметы из матчевого рюкзака, выводит героя из очереди и клетки, сохраняет отдельный `hex_player_results`, ledger и revisions. Повтор `commandId` возвращает прежний ответ, а иной ID после выхода отклоняется. `MATCH_PATCH` рассылается после commit. Другие игроки продолжают матч; последний вышедший завершает его.

Награды используют `CalculateResultsFromEvents`: 20 золота за выживание, 8 за убитого монстра и `damageTotal/50`; опыт — `damageMonsters/5` (и существующая формула PvP для событий игроков). Выход с квестом добавляет Square-бонус победителя 100 золота и 120 XP. Платный выход списывает ровно 50 золота постоянного профиля, без квестового бонуса. Все начисления выполняются только при успешной эвакуации; при смерти результат содержит нулевую награду и потерянные вещи. XP применяется к герою матча по прежним порогам уровней. Таким образом, в новом одиночном HEX PvE герой с нулём золота может получить артефакт, выйти бесплатно и получить первую награду. Пользователь подтвердил в браузере успешную эвакуацию с артефактом, 120 золота и перенос добычи в постоянный Storage; остальные ветки этого абзаца требуют отдельной ручной проверки.

Результат каждого героя переживает reload через `hex_player_results` и HEX snapshot: способ выхода или смерть, золото, XP, перенесённый или потерянный рюкзак и снаряжение. `/game` показывает экран результата на en/ru/de и блокирует действия. Старый Square-финализатор не вызывается. Существующая история матчей (`match_stats`/`match_player_stats`) пока не наполняется этим узким HEX-путём: сохранённый результат доступен через HEX snapshot, но отдельный экран общей истории ещё не интегрирован. `hex-test` не даёт эвакуироваться, чтобы тестовый API без списания Loadout не выдавал награды постоянному профилю. PvP, постройки и другие прежние ограничения HEX остаются.

Ручная проверка после обеих миграций: создать **обычный** PvE HEX-матч через меню с профилем без золота, подобрать материал и открыть бочки до квестового артефакта, завершить несколько ходов, встать на портал и выбрать бесплатный выход. Проверить экран результата, `player_profiles.balance` (как минимум 120 золота при отсутствии иных событий), сумму нового и старого Storage, отсутствие квестового артефакта в Storage, пустой матчевый рюкзак, reload и следующий матч с балансом и предметами. Отдельно проверить платный выход с профилем ≥50 золота и без артефакта: подтверждение, списание ровно 50, базовая/боевая награда только после выхода. Повторить тот же `commandId`, отправить другой ID после выхода и параллельные запросы; изменения профиля и `hex_player_results` должны остаться однократными. В матче нескольких игроков вывести одного и убедиться, что второй получает `MATCH_PATCH`, остаётся активным по очереди и может продолжить игру. Для смерти проверить потерю рюкзака, выпадение квеста, нулевую награду и экран Defeat после reload. Эти сценарии здесь не запускались: PostgreSQL, Docker и браузер исключены ограничениями задачи.

Есть read-only preview, отдельный однопользовательский тестовый матч и обычный матч через существующий matchmaking. При `HEX_MATCH_ENABLED=true` стандартный `/game/createMatch` сохраняет `hex-v1` для выбранного в меню режима; без флага Square-путь остаётся действующим. Все HEX-матчи открываются на обычном `/game?instance_id=<instanceId>`. `/hex-lab` остаётся инструментом прототипирования. HEX snapshot использует `schemaVersion: 2`, `geometry: hex-v1` и позиции `{q,r}`.

## HEX на обычном игровом экране

Выберите героя и режим в обычном меню, нажмите `Join Queue` и дождитесь матча. Matchmaking передаёт прежние `RequestMatch`, команды и `turn_order`; `GameWrapper` сначала читает `/game/match`, а при `hex-v1` загружает `/game/hex/{instanceId}`. Для прежнего тестового матча используется `/game/hex-test/{instanceId}`. Square Redux и обработчики `x/y` получают только square snapshot. HEX-карта использует общий с HEX Lab компонент `HexMap`; правила движения, PvE, подбора и хода остаются серверными.

На игровом экране показаны серверные HP, энергия, класс, дальность, ловкость, герой, монстры, ресурсы, номер хода и revisions. Используются существующие `PlayerHUD`, `ActionLog`, `Inventory` и оболочка игрового экрана. Журнал показывает действия текущей клиентской сессии; история событий после reload пока не восстанавливается в HUD. Инвентарь поддерживает уже перенесённые предметы и свитки; постройки и связанные кнопки Square пока недоступны для HEX. Миникарта, 3D и Square HUD объектов остаются Square компонентами. После смерти и выхода HEX snapshot загружается с сохранённым персональным результатом.

Два клика по свободной клетке запрашивают маршрут и выполняют движение. Клик по монстру, его подписи или клетке под ним выбирает цель; только кнопка «Атаковать» отправляет удар. После попадания панель сохраняет цель, новые HP, эффекты и доступное действие; она закрывается при явном закрытии, смерти или недоступности цели. Клик по герою позволяет выбрать ресурс под его клеткой. Подбор и завершение хода доступны в правой панели. Повторная попытка после ошибки использует прежний `commandId` для той же команды. Подключение WebSocket посылает `JOIN_MATCH`, принимает `MATCH_UPDATE` с HEX snapshot и после `MATCH_PATCH` перечитывает snapshot; меньшая `stateRevision` игнорируется. WebSocket проверяет участника матча. Reload также читает PostgreSQL.

В браузерном тесте 19.10.2026 локальный GameService и изолированная PostgreSQL использовались с тестовым профилем Mystic; для проверки клиентской сессии работал локальный тестовый auth endpoint. Матч создан настоящим `POST /game/hex-test`; в этой тестовой БД монстр и ресурс были поставлены рядом с героем для воспроизводимой цепочки. Headless Chrome открыл `/game` без `/hex-lab` и выполнил маршрут, движение, удар, подбор food, открытие инвентаря, завершение хода и reload. Получены `stateRevision/mapRevision = 5/3`, предмет `resource_1 ×1`, `MATCH_UPDATE` revision 1 и `MATCH_PATCH` revisions 2–5; ошибок JavaScript не было. Отдельный square матч создан через обычный `/game/createMatch` и на том же `/game` отрисовал Square карту.

До полноценного PvP нужно перенести атаки между игроками и соответствующие классовые эффекты. Постройки, общий экран истории матчей и оставшиеся Square-механики остаются отдельными этапами.

## Запуск без базы данных

В двух терминалах из корня проекта:

```sh
cd beckend/gameservice && go run ./cmd/hex-preview
```

```sh
NEXT_PUBLIC_API_BASE=http://127.0.0.1:18081 npm run dev
```

Открыть <http://localhost:3000/hex-lab>. Seed меняет воспроизводимую карту; клик по клетке показывает `(q,r)` и terrain. `GET http://127.0.0.1:18081/game/hex-preview?seed=1` возвращает тот же JSON. В обычном GameService этот read-only маршрут доступен только при `HEX_PREVIEW_ENABLED=true`.

`GenerateDungeon(config, catalogs, seed)` строит конечный HEX-диск, комнаты, коридоры к центральной области, непроходимый камень и стены на границах пола с камнем. Это чистая функция без SQL. Радиус выбирается по числу участников и команд, затем проверяется фактическое число проходимых клеток; при нехватке места генерация повторяется с большим радиусом либо возвращает ошибку. Одинаковые конфигурация, каталоги и seed дают одинаковую карту. Preview вызывает этот же генератор с иллюстративным каталогом для одного игрока.

Стартовые клетки выделяются по одной области на команду, без наложений; участники команды расположены рядом. Портал получает настоящую проходимую HEX-клетку около центра, отличную от `(0,0)`. Генератор резервирует маршруты от всех стартов до портала, поэтому монстры и бочки не перекрывают достижимость. На остальных допустимых клетках используются шансы Square `GenerateFullMap()` для монстров (5%), бочек (10%) и ресурсов (10%). Монстры и ресурсы берутся из переданных каталогов. Бочка определяется по типу `barrel`/`barbel`, с совместимым fallback на ID 6. Генератор только размещает бочки и портал; открытия и эвакуации здесь нет.

## Тестовый игровой матч

Нужны локальная **отдельная тестовая** PostgreSQL, применённые вручную `stage1_geometry.sql` и `stage2_commands.sql`, действующий JWT аккаунта с выбранным героем в этой тестовой базе. Никогда не направляйте следующие команды на пользовательскую БД.

После создания пустой локальной БД с именем, содержащим `test`, из корня проекта:

```sh
export HEX_TEST_DB_DSN='postgres://USER@127.0.0.1:PORT/nachalo_hex_test?sslmode=disable'
cd beckend/gameservice && go run ./cmd/hex-test-schema
cd ../..
psql "$HEX_TEST_DB_DSN" -v ON_ERROR_STOP=1 -f docs/hex-migration/stage1_geometry.sql
psql "$HEX_TEST_DB_DSN" -v ON_ERROR_STOP=1 -f docs/hex-migration/stage2_commands.sql
psql "$HEX_TEST_DB_DSN" -v ON_ERROR_STOP=1 -f docs/hex-migration/stage3_hex_pve.sql
```

Запустить GameService с `GAME_DB_DSN=$HEX_TEST_DB_DSN`, `HEX_TEST_MATCH_ENABLED=true`, `HEX_PREVIEW_ENABLED=true` и обычным тестовым `JWT_SECRET_KEY`. Из корня проекта запустить frontend с `NEXT_PUBLIC_API_BASE=http://127.0.0.1:8001`, `NEXT_PUBLIC_WS_URL=ws://127.0.0.1:8001/ws` и адресами локальных тестовых auth/matchmaking сервисов. Войдите в тестовый аккаунт, у которого есть профиль и выбранный герой в этой GameService БД, откройте `/hex-lab` и нажмите «Создать игровой HEX-матч». URL получит `?match=hex-test-…` и после обновления страницы загрузит матч из PostgreSQL.

Первый клик по HEX-клетке запрашивает серверный маршрут, показывает число шагов и стоимость. Второй клик по той же клетке подтверждает команду с `commandId`. Сервер повторно проверяет очередь, маршрут и энергию внутри `MatchCommand`; сохранение позиции, энергии и занятости клеток, ledger и revisions проходит одним commit. `MATCH_PATCH` отправляется после commit. Повтор команды возвращает прежний результат без повторной рассылки.

Тестовый матч остаётся однопользовательским. И тестовый, и обычный матч используют одну атомарную HEX-материализацию: выбранные герои и эффективные характеристики экипировки, команды, карту, старты, портал, монстров, бочки и ресурсы. Для подбора нужно сначала встать на клетку ресурса `(q,r)`, затем выполнить отдельную команду «Подобрать». Square UI также использует отдельное действие на текущей клетке; движение само по себе не подбирает ресурс. HEX проверяет полное совпадение координат внутри `MatchCommand` до записи инвентаря и карты. При отказе остаются прежними JSON-инвентарь, `inventory_items`, ledger и revisions. Успешный подбор проходит одним commit; повтор `commandId` возвращает исходный результат. После commit HEX Lab обновляет snapshot.

Кнопка «Завершить ход» передаёт ожидаемый номер раунда. Однопользовательская очередь переходит к тому же игроку и следующему раунду, восстанавливая энергию по существующему шаблону класса. HTTP и 60-секундный таймер вызывают один `ApplyHexEndTurn` под блокировкой матча: просроченный таймер отклоняется, состояние и событие сохраняются после одного commit. Ресурсы не тратят энергию. Изменения карты повышают `mapRevision`; завершение хода повышает только `stateRevision`. Сгенерированные бочки и портал хранятся на карте, но взаимодействия с ними пока недоступны; команда завершения хода отклоняет неподдерживаемые постройки. После рестарта таймер запускается снова при загрузке HEX snapshot; исходный deadline пока не хранится в PostgreSQL.

HEX Lab позволяет выбрать монстра. Первый клик запрашивает `/attack-preview` и показывает HEX-дистанцию, режим и цену энергии; второй клик по тому же monster ID либо кнопка «Атаковать» отправляет `/attack` с `commandId`. Сервер повторяет проверку под `MatchCommand` после блокировки строки матча. Дальность считается из `(q,r)`, для ближней атаки нужна соседняя клетка, а line of sight проверяет пересечение центра луча со стенами и непроходимым камнем. Положение и цену из клиента сервер не принимает. HP и результаты обмена отображаются после commit; `MATCH_PATCH` служит сигналом загрузить новый snapshot. Старые square `/move`, `/attack`, `/collectResource` и `/endTurn` явно отклоняют `hex-test`.

HEX PvE использует исходные чистые функции `applyDamage`, `applyFlatDamage`, `tryApplyRangerCriticalShot`, `resolveAttackEnergyCost`, `resolvePresentationAttackStyle` и те же константы/порядок из square combat. Для поддерживаемых веток HP/энергия, контратака, смерть монстра, существующий equipment drop, `combat_result_events`, ledger и revisions сохраняются одной транзакцией. Дроп экипировки по действующему правилу сразу выдаётся владельцу через `item_instances`; это не предмет на клетке для подбора. `mapRevision` растёт при удалении монстра, `stateRevision` — один раз за атаку. PvP в однопользовательском формате отсутствует.

| Guardian | Ближний удар, контратака монстра, Guardian response, смерть монстра и дроп | Да: ответный урон, смерть/дроп, replay/rollback, смертельная контратака | Aura против игроков в этом формате неприменима |
| Mystic | Ближний и дальний удар, прежнее снижение защиты монстра до 60%, ближняя контратака | Да: оба режима и формула урона | Quest artifact эффекты; матч их явно запрещает |
| Berserker | Ближний удар, lifesteal, уменьшение контратаки до 55%, дополнительный удар | Да: все перечисленные эффекты с принудительным RNG в тесте | PvP механики вне однопользовательского формата |

Armor Break хранится в `match_monsters.hex_armor_break_stacks` и `hex_armor_break_turns`, а не только в памяти процесса. На каждом завершённом HEX ходе срок уменьшается; на третьем попавшем дальнем выстреле стеки сбрасываются. Порядок прежний: основной урон с текущим штрафом защиты, затем critical shot, затем эффект третьего выстрела. Push выбирает ближайшее направление axial HEX к лучу атаки, проверяет границы карты, камень, стены и занятость; координаты монстра и revisions сохраняются в одном `MatchCommand`. При невозможном Push действует прежний дополнительный урон в половину рассчитанного урона с прежним минимальным значением.

Смертельная контратака и внутренняя атака монстра используют тот же ledger и транзакцию, что и урон, HP, энергия, события результатов, очередь и клетка. `ApplyHexMonsterAttack` — только внутренняя серверная функция, отдельного HTTP маршрута от имени монстра нет. Повтор `commandId` возвращает сохранённый результат без второго урона и без повторной публикации. Если погибает единственный игрок, тестовый матч получает `active_user_id=0`, `turn_order=[]`, свободную клетку и `finished_at` в том же commit. Его `combat_results_complete=false`, поэтому награды не начисляются и отдельная legacy финализация не запускается. Такой завершённый матч остаётся доступен для replay по ledger, но обычный HEX snapshot не загружается как живой матч.

Ограничения: обычный matchmaking создаёт HEX при `HEX_MATCH_ENABLED=true`; прежний тестовый API остаётся однопользовательским под `HEX_TEST_MATCH_ENABLED`. Для будущего открытия бочки действует то же правило позиции: игрок должен стоять на её HEX-клетке; HEX-команды открытия пока нет, исходы должен определять существующий `OpenBarbel()`. PvP, турели, открытие бочек, использование портала и quest artifact не реализованы для HEX. Нет автоматического планировщика атак монстров: внутренняя функция выполняет переданную сервером команду, но тестовый ход сам её не вызывает. Не сохранён deadline таймера между перезапусками, нет серверной фильтрации видимости и полной наградной финализации. Полным PvE или PvP режим объявлять нельзя.

## Обычный многопользовательский HEX-матч (20.10.2026)

При `HEX_MATCH_ENABLED=true` GameService принимает обычный `RequestMatch` от действующего matchmaking, использует его нормализованные команды, `turn_order`, выбранных героев и эффективные характеристики экипировки. Один commit сохраняет `hex-v1` матч, игроков с `group_id`, стартовые `(q,r)`, каталог монстров, ресурсы, бочки и портал. Matchmaking сохраняет прежние очередь, режимы, SSE-уведомление и маршрут входа. Для запуска: войти в аккаунт, выбрать героя в таверне, открыть `Modes` (`/mode`), выбрать режим, нажать `Join Queue`, после подбора открыть предложенный `/game?instance_id=<instanceId>`. Тестовый `/hex-lab` не нужен.

Для реального развёртывания требуется применённая HEX schema Stage 1–3 и включённый `HEX_MATCH_ENABLED`. Основная PostgreSQL в этом этапе не менялась: на 20.10.2026 основной Docker GameService сообщает об отсутствующем `hex_stage1_migration_marker` и перезапускается. Описанный ниже рабочий цикл проверен на отдельной PostgreSQL с миграциями, а не на основной базе.

Доступные обычные режимы при включённом флаге: `PVE` (1), `1x1` (2), `1x2` (3 команды по действующей нормализации), `2x2` (4), `3x3` (6), `5x5` (10). PostgreSQL проверил материализацию составов 1, 2, 3, 4, 6 и 10 участников; браузерный полный цикл проверен для двух участников `1x1`. Остальные режимы пока не проходили браузерный E2E.

HEX snapshot проверяет участника матча и содержит его собственный инвентарь и энергию. Остальные игроки представлены на карте именем, командой, HP и позицией, без личного инвентаря и характеристик атаки. Как и действующий Square snapshot, текущая серверная карта целиком видна участникам: серверная фильтрация видимости ещё не реализована. WebSocket проверяет членство перед отправкой HEX patch и отправляет персональный snapshot после `JOIN_MATCH`; общий patch содержит только публичные идентификаторы, координаты и revisions, после чего клиент перечитывает личный snapshot. Публикация происходит после commit; replay не публикует второй patch.

Ход переходит к следующему живому участнику по сохранённому `turn_order`; номер раунда увеличивается после возврата к началу очереди. Энергия восстанавливается следующему игроку по прежнему шаблону класса. HTTP и таймер используют один транзакционный `ApplyHexEndTurn`. Смерть активного игрока от контратаки удаляет его из очереди, освобождает клетку и передаёт ход выжившему в том же commit; смерть последнего завершает матч без неполных наград.

На отдельной PostgreSQL тесты подтвердили создание и повторную загрузку общего матча, отказ постороннему пользователю, отсутствие чужого инвентаря в snapshot, движение и смену ходов, replay `commandId`, отказ неактивному игроку, конкурентное завершение хода с одним победившим commit, rollback хода и rollback создания матча. Отдельный PvE-тест подтвердил смертельную контратаку в двухпользовательском матче и передачу хода выжившему.

Настоящий браузерный E2E запустил AuthService, matchmaking, GameService, Next.js и отдельные auth/game PostgreSQL. Два зарегистрированных пользователя в независимых браузерных контекстах выбрали `PvP 1x1` в обычном `/mode` и нажали `Join Queue`. Matchmaking создал один матч `d2f88c73-9b9c-4d74-895f-e0aa8192d6db` с очередью `[4,3]`. Оба вошли в `/game`, увидели одинаковую карту; первый переместился и завершил ход, второй получил WS-обновление, переместился и завершил ход, первый получил обновление. После reload оба увидели `stateRevision/mapRevision=5/3`, раунд 2 и одинаковые клетки. Каждый браузер получил `MATCH_UPDATE` и четыре `MATCH_PATCH`; ошибок JavaScript не было. Позже отдельный SQL-запрос зафиксировал последовательные команды таймера `hex-timer:2:4`, `hex-timer:2:3`, `hex-timer:3:4` и состояние `8/3`, раунд 3; таймер продолжил чередовать игроков. Это проверка совместного игрового цикла, но не PvP-атаки.

После сокращения общих WebSocket payload браузерный сценарий повторён на новой паре аккаунтов `[7,8]`: оба получили четыре `MATCH_PATCH` и завершили цикл с `5/3`; ни один patch не содержал полей `inventory`, `energy` или `drops`.

## Игровой вид HEX-карты для MVP (20.10.2026)

Обычный `/game` использует прежний `HexGameController` и общий `HexMap`. Серверный snapshot и WebSocket вынесены в `useHexMatchSnapshot`, управление камерой — в `useHexCamera`; выбор клетки, маршрут и команды остались в контроллере. Карта больше не вписывает всё подземелье в экран: начальный кадр центрируется на герое и показывает крупные клетки. Положение камеры не сбрасывается от изменения snapshot, WebSocket, атаки или открытия инвентаря.

Пол и камень используют имеющиеся локальные текстуры Nachalo, стены выделены отдельными рёбрами. Для известных классов героев, монстров и ресурсов используются локальные изображения; при отсутствии изображения остаётся простая SVG-иконка. Сохранились общие `PlayerHUD`, `Inventory`, `ActionLog` и панель атаки; панели размещены по краям, а координаты и revisions находятся в раскрываемой диагностике. Правила действий и серверная геометрия не менялись.

Настоящий браузерный E2E запустил Chrome, GameService и отдельную временную PostgreSQL. Проверены крупная клетка около 88×100 px на рабочем экране 1600×1000, zoom колёсиком, pan без отправки команд, возврат камеры к герою, сохранение камеры при открытии инвентаря, ручном обновлении и WebSocket patch. Браузер выполнил движение двумя кликами, отдельный подбор ресурса, выбор монстра, два удара с открытой панелью и третий смертельный удар с закрытием панели. После этого проверены окно 850×600 и reload; JavaScript-ошибок не было. Fixture для боя передвигал героя и изменял HP существующего монстра только во временной тестовой базе. TypeScript checker, Node-тесты и production build прошли.

Рендерер остаётся двумерным SVG и использует временные значки для объектов без готового изображения. Для будущего Three.js можно сохранить snapshot, HEX-координаты, контроллер действий и обработку WebSocket, заменив отображение карты и управление камерой. PvP-атаки, открытие бочек, постройки, артефакт, портал и награды по-прежнему не реализованы в этом виде.

## Бочки и предметы в HEX (20.10.2026)

На обычном `/game` герой может пройти на клетку бочки и открыть её отдельной кнопкой только при точном совпадении `(q,r)`. Команда повторно проверяет позицию и очередь под блокировкой `MatchCommand`. Для исхода используется прежняя `game.OpenBarbel()` с вероятностями 30% урона (3–5 HP), 40% ресурса и оставшимся шансом артефакта. Урон и смерть записываются в `combat_result_events`; при смерти обновляются очередь, клетка и состояние завершения матча. Завершённый HEX snapshot остаётся доступным участнику для отображения итогового HP и состояния после reload, но действия блокируются. Ресурс или артефакт записывается в JSON-инвентарь и `inventory_items`; бочка удаляется. Все изменения, ledger и revisions проходят одним commit. Replay `commandId` возвращает исходный результат и не публикует второй WebSocket patch.

HEX-инвентарь использует прежний компонент `Inventory`. Еда и вода берут эффект из каталога `resources`; еда доступна один раз за два хода, вода — не более пяти применений за два хода. Лимиты считаются по сохранённым командам матча, поэтому переживают перезапуск сервиса и проверяются внутри транзакции. Поддержаны все шесть существующих свитков: координаты портала, ближайшего другого живого игрока и ближайшей бочки. Square-оси X/Y на HEX представлены осями q/r, а «ближайший» определяется HEX-дистанцией. Использование предмета расходует одну копию из инвентаря этого матча; профильный инвентарь не списывается второй транзакцией. Чертежи отображаются как недоступные, пока нет HEX-строительства, и не расходуются. Старые Square HTTP-обработчики использования предметов, свитков, бочек и чертежей отклоняют `hex-v1` матч.

PostgreSQL integration-тесты на отдельной базе подтвердили отказ открыть бочку из соседней клетки без изменений, движение на бочку, все три исхода, смерть единственного игрока, журнал событий, replay, rollback без WS, обычный многопользовательский HEX-матч, эффекты еды и воды, лимиты, все шесть свитков с доступной целью, конкурентное использование единственного предмета, revisions и отсутствие двойного расхода. Настоящий Chrome с GameService и отдельной временной PostgreSQL прошёл все три случайных исхода в повторных прогонах, затем использование еды, воды и свитка портала, отказ от использования чертежа, пять `MATCH_PATCH` после commit и reload без JavaScript-ошибок. Остальные свитки проверены PostgreSQL-тестами; свиток ближайшего игрока требует другого живого участника.

Ограничение: HEX-матч пока создаётся без `quest_artifact_id`, поэтому артефакт из бочки хранится как обычный каталожный артефакт; принудительное выпадение квестового артефакта из последней бочки, эвакуация и награды ещё не подключены. Этот этап не делает квестовый артефакт или портал готовыми.

## HEX UX: взаимодействия, HUD, смерть и языки (20.10.2026)

Кнопка `Pick up` или `Open` в обычном `/game` теперь определяется клеткой `(q,r)` самого героя в авторитетном HEX snapshot. Выбирать клетку повторно не нужно. Кнопка исчезает после commit и обновления snapshot; во время команды, чужого хода, смерти или завершения матча она заблокирована. Синхронный клиентский guard не даёт повторному клику отправить вторую команду до ответа. Серверные проверки позиции и очереди, `commandId` и отдельное действие подбора после движения сохраняются.

Камера меняет только SVG world через `viewBox`; HUD, журнал, инвентарь, панель атаки, сообщения и кнопки остаются вне трансформируемого поля. Панели закреплены относительно оболочки игры и получают прокрутку по высоте в небольшом окне. Строка с содержимым инвентаря удалена из правого HUD; предметы остаются в общем `Inventory`.

Серверная смерть последнего игрока уже выставляет `finished_at` в той же транзакции, а HEX snapshot возвращает `finished=true` и HP героя. Клиент теперь показывает `Defeat` и `Return to Menu`, убирает маршрут и цель и блокирует команды; этот результат восстанавливается после reload. Смерть одного игрока в продолжающемся многопользовательском матче не объявляет весь матч завершённым.

Для HEX игрового интерфейса добавлен общий словарь `en` (по умолчанию), `ru`, `de` и переключатель в HUD с сохранением в `localStorage`. Переведены команды, подсказки, сообщения клиента, карта/камера, диагностика, общие HUD и инвентарь при использовании в HEX. Имена игроков, названия предметов и произвольные серверные ошибки остаются исходными. Остальные разделы приложения пока не локализованы.

На этом этапе выполнены только `npx tsc --noEmit` и проверка diff; Docker, PostgreSQL, браузерный E2E, полные тесты и production build не запускались по требованию пользователя. Требуется ручная проверка после `docker compose up --build -d`: кнопка под героем до/после подбора и открытия бочки, быстрые двойные клики, zoom/pan при открытых панелях на обычном и малом окне, смерть единственного героя и reload, смерть участника живого многопользовательского матча, смена языка и его сохранение.

## Storage и Loadout: первый этап экономики HEX (20.10.2026)

Постоянный склад — существующий `player_profiles.inventory`; золото — `player_profiles.balance`, экипировка — существующие `item_instances` и `character_equipment`. Новая таблица склада не создаётся. Магазин добавляет купленные расходники в профильный склад; покупка переведена на транзакцию с блокировкой строки профиля, чтобы не перезаписать параллельный перенос набора. Постройки базы уже списывали дерево, камень и железо из этого же профиля под блокировкой.

В базе показывается Storage, а в обычном меню `/mode` — Storage и выбор Loadout. Поддерживается сохранение количеств еды, воды, каталожных ресурсов с эффектом здоровья/энергии, шести существующих свитков и трёх существующих чертежей. Дерево, камень и железо нельзя выбрать. Проверка ключа и количества выполняется сервером. Выбор хранится в новом поле `player_profiles.hex_loadout`; до создания матча склад не уменьшается, поэтому выход из очереди не требует возврата предметов. В групповом матче каждый участник сохраняет свой набор самостоятельно.

При обычном `CreateHexMatch` профили участников блокируются в порядке ID. В той же транзакции создаются карта, игроки и их отдельные рюкзаки, выбранные количества вычитаются со склада, а выбор очищается. Для еды, воды, других ресурсов и свитков создаются строки `inventory_items`; чертежи остаются в JSON рюкзака, пока HEX строительство не поддерживается. Старое копирование всего профиля в каждый HEX матч убрано. Повторное создание с тем же `instanceId` откатывает и списание склада. Если одновременно создаются два матча для одного профиля, блокировка строки не позволяет перенести одну и ту же копию дважды. В HEX инвентаре по-прежнему показывается только рюкзак конкретного матча.

Служебный режим `hex-test` создаётся с пустым рюкзаком и не списывает постоянный склад, даже если в профиле сохранён Loadout.

Перед использованием этого этапа необходимо **вручную** применить [stage4_storage_loadout.sql](stage4_storage_loadout.sql) к нужной игровой БД. Агент миграцию не применял. Для isolated PostgreSQL добавлены `TestHexStorageLoadoutAtomicPostgres` и `TestHexStorageConcurrentCreatePostgres` с проверками передачи, нормализованного инвентаря, отказа при нехватке, rollback повторного создания и однократного переноса при конкурентном создании; их запуск оставлен пользователю. Локально прошли `gofmt`, целевой `go test` без БД, `npx tsc --noEmit` и `git diff --check`.

**Этап экономики не завершён.** Квестовый артефакт, эвакуация за артефакт или 50 золота, перенос добычи обратно на склад, выплаты за монстров и опыт, удаление рюкзака при смерти и окончательная обработка выпавшей в матче экипировки пока не подключены. Существующая выдача equipment drop в `item_instances` остаётся прежней и ещё не обеспечивает требуемую защиту рискованной добычи до эвакуации. Старую Square финализацию для HEX включать нельзя: её неполная история событий и прямое копирование инвентаря не соответствуют этому этапу. Следующий минимальный этап — транзакционные смерть и оба варианта эвакуации с однократным переносом/выплатой, затем полный PostgreSQL и браузерный прогон на отдельной БД.
