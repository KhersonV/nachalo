# NACHALO: проект единой HEX-модели

Этот документ описывает будущую реализацию. Ни DTO, ни маршруты API, ни новые функции ниже ещё не реализованы. Проверенные текущие места изменения перечислены в [ARCHITECTURE_AUDIT.md](ARCHITECTURE_AUDIT.md).

## 1. Выбор модели и контракт

| Модель | Преимущества | Ограничения | Назначение |
|---|---|---|---|
| Axial `(q,r)` | Два целых числа; единые шесть векторов; нет parity-ветвлений | Область не обязана быть прямоугольной; нужна проекция | Канонические backend, DB, API, Redux, клеточные эффекты |
| Cube `(x,y,z)`, x+y+z=0 | Простые distance, rounding, rings, lerp | Третья координата избыточна; риск неверного invariant в API | Внутренние вычисления, не wire format |
| Offset odd/even row/col | Удобная прямоугольная таблица | Чётность, отрицательные индексы, неодинаковые neighbor deltas | Только при необходимости импорт/экспорт; не основной формат |

| Ориентация | Плюсы | Минусы |
|---|---|---|
| Pointy-top | Горизонтальные пары соседей, удобные ряды Classic/minimap, простая общая XZ-проекция | Диагональные edge стены требуют новых transforms; q/r не экранные x/y |
| Flat-top | Вертикальные пары соседей, удобные колонки | Другой layout и клавиатурные подписи; не даёт выигрыша существующим square meshes |

Рекомендация: **axial, pointy-top**. Текущая ось мира Y остаётся высотой Three.js; плоскость карты — world X/Z. Никакой серьёзной причины выбирать offset в коде не выявлено. Существующие wall meshes всё равно требуют переработки при обеих ориентациях.

Будущий wire envelope:

```json
{
  "schemaVersion": 2,
  "geometry": { "kind": "hex", "coordinates": "axial", "orientation": "pointy", "version": 1 },
  "instanceId": "example-match",
  "mapRevision": 1,
  "stateRevision": 42,
  "cells": [{ "cellId": 17, "position": { "q": 0, "r": 0 }, "terrain": "floor" }]
}
```

Это пример структуры, а не разрешение послать все server cells клиенту. Viewer snapshot содержит только разрешённые клетки и объекты. Неизвестная геометрия/версия отклоняется с запросом совместимого клиента; отсутствие версии означает **legacy square**, никогда HEX. HexCoord содержит только конечные безопасные целые, в Go — ограниченные допустимым доменом значения; валидировать до distance/abs, чтобы исключить overflow. `cellId` стабилен внутри `(instanceId,mapRevision)`, не вычисляется как `r*width+q`. Отдельный `coordKey(q,r)` с явным разделителем и signed integer parser.

`mapRevision` меняется при изменении схемы топологии/набора клеток; runtime edge/structure изменения также увеличивают `stateRevision`. Декорация может иметь собственный revision. Width/height становятся визуальными bounds, не правилом существования клетки. Во всех структурах игрока, монстра, квеста, дропа, старта, портала, push и combat snapshots использовать один `position:{q,r}`. WorldPoint `{X,Y,Z}` и ScreenPoint `{left,top}` — отдельные типы; не хранить дробные координаты анимации в HexCoord.

## 2. Математика и граничные соглашения

Пусть `a>0` — радиус до вершины. Индексы направлений фиксированы во всех языках:

| i | Δq | Δr | X/Z при pointy-top |
|---:|---:|---:|---|
| 0 | 1 | 0 | вправо |
| 1 | 1 | -1 | вправо-вверх |
| 2 | 0 | -1 | влево-вверх |
| 3 | -1 | 0 | влево |
| 4 | -1 | 1 | влево-вниз |
| 5 | 0 | 1 | вправо-вниз |

`neighbor(h,i)=h+dirs[i]`; opposite=`(i+3)%6`. Cube: `(x,y,z)=(q,-q-r,r)`; обратно `(q,r)=(x,z)`. Для Δ между двумя клетками:

`D=(|Δq|+|Δr|+|Δq+Δr|)/2 = max(|Δq|,|Δr|,|Δq+Δr|)`.

Каждый шаг меняет две cube-оси на ±1, значит уменьшить D можно максимум на 1. Пока не достигнута цель, существует сосед с D-1. Поэтому D — кратчайшее число шагов на свободной HEX-решётке; при стенах это нижняя граница длины пути.

Проекция центра (до camera transform):

`X=a√3(q+r/2)`, `Z=3ar/2`; Three.js `(X,elevation,Z)`, Classic `(X,Z)` после scale/translation. Обратная: `qf=(√3 X/3-Z/3)/a`, `rf=2Z/(3a)`. Подстановка даёт qf=q, rf=r. Все шесть векторов соседей имеют world длину `a√3`. Для первоначального сохранения длины нынешнего world шага=1 выбрать `a=1/√3`; ширина HEX=1, высота=2/√3. Это стартовая шкала рендера, не решение о числе клеток. Скорость Ranger 2.75 units/s тогда не меняет длительность шага по направлению.

Вершины: угол `π/6+kπ/3`, k=0..5. Flat-top потребовал бы `X=3aq/2`, `Z=a√3(r+q/2)` и углы kπ/3; обе системы не смешивать.

Округление: получить cube float `(xf,yf,zf)=(qf,-qf-rf,rf)`, округлить все оси, найти максимальную абсолютную ошибку, заменить соответствующую rounded ось на минус сумму двух других. На равной ошибке фиксировать приоритет x→y→z. Для половин использовать одинаковое правило в Go/TS: `floor(v+0.5)`, в том числе при отрицательных значениях; нормализовать -0. После rounding проверить **наличие клетки в домене**. Численные допуски и tie cases закрепить общими fixtures.

Picking Classic: client→локальные координаты SVG/canvas/DOM слоя через обратный scale/translation → inverse projection → cube round → domain и видимость. Polygon hit-test на границе использует тот же tie policy. Three.js: NDC из boundingClientRect → ray на плоскость пола → inverse projection; при разных высотах предпочтительнее pick разрешённого mesh с cellId. Лучи на персонажей имеют приоритет над полом, но только для полученных видимых объектов. `Math.round(worldX/worldZ)` удалить.

Границы: `cellsByCoord.has(q,r)`, а не q/r>=0. Для предлагаемого диска радиуса R: `max(|q|,|r|,|q+r|)<=R`; допускается sparse irregular footprint. Камера clamp-ится по projected world bounds/допустимому padding, не по прежним width/height.

Кольцо k>0 содержит 6k клеток: начать в `center+dirs[4]*k`, пройти по k шагов направлений 0..5, добавляя позицию до шага. k=0 — центр. Диск радиуса k содержит `1+3k(k+1)`. Range overlay перечисляет диск и затем фильтрует domain/LOS; это не утверждение атакуемости каждой клетки.

Во время аудита независимым вычислением проверены проекция↔обратная для 1681 центра q,r∈[-20,20], равная длина шести соседей, размеры колец/дисков k=1..10. Это проверка формул, не тест будущего Go/TS-кода. Расширенные round/graph fixtures описаны в RISKS_AND_TESTS.

## 3. Клетки, стены и общие предикаты

Разделить `terrain` (floor/rock/void), содержимое клетки (resources/barrel/portal/units), cell structures (base/scout_tower/turret/wall) и **edge walls**. Legacy `structure_type=wall` остаётся клеточным строением; превращение всех таких стен в edge walls меняло бы размер и стоимость строительства.

Ребро хранить один раз: canonical pair соседних координат с лексикографическим порядком `(q,r)`; endpoint отсутствующей клетки — boundary с отдельным правилом. У edge: blockMovement, blockSight, kind=wall/door/open, состояние двери, revision. Шестибитная маска на клетке допустима как derived cache; invariant `edge(A,i)==edge(B,opposite(i))` обязателен. Визуализация получает то же canonical ребро и его midpoint/normal, не угадывает препятствие по соседним meshes.

Будущие общие операции (предлагаемые имена, файлов пока нет): `Neighbors`, `HexDistance`, `CanTraverse`, `CanSee`, `CanAttack`, `CanInteract`, `StepCost`. Для traversal нужны: обе клетки существуют, HEX соседство, не blockMovement edge, terrain/structure разрешает вход, destination свободна от живого unit. Союзник не цель автоматической атаки и не проходимая клетка. Одновременный swap на первом этапе запрещён.

LOS — геометрия взгляда, не camera occlusion. Использовать supercover отрезка центров в cube/world плоскости с учётом **всех пересечённых HEX-клеток и рёбер**. На совпадении отрезка с ребром/вершиной применяется консервативное правило: блокирующее касаемое ребро препятствует выстрелу; смотреть/стрелять через точечную щель нельзя. Простой cube lerp+round — полезный черновой line, но недостаточен на ties: требуется дополнить touched cells/edges и проверить symmetry `LOS(A,B)=LOS(B,A)`. Проверка препятствий промежуточных клеток, входного ребра цели, высоты/opacity фиксируется единообразно; границу самого origin не считать помехой. Для opaque rock клетки разрешить видеть её обращённую поверхность, но не стоящего за ней unit. Стена не обязана блокировать магическую ауру: это отдельный параметр способности.

Pathfinding: Dijkstra для reachable/cost budget, A* для выбранной цели с heuristic=`HexDistance*minStepCost` (min>=1). BFS только при доказанно постоянной цене. Детерминированный tie-break `(f,g,q,r)` и фиксированный порядок соседей. Не считать Euclidean heuristic по axial q/r. При first-step Boots и накоплении aura pressure состояние поиска расширяется хотя бы на `(coord,firstStepUsed,auraPressure)`; если требуется оптимизация с учётом выживания — добавить HP. Иначе нельзя обещать глобально минимальную допустимую цену по одному `g[coord]`. Первая версия запрещает петли и выбирает минимальную энергию среди безопасных путей текущего хода; при равенстве — меньше шагов. Известное смертельное ребро помечается опасным и требует отдельного решения UX, по умолчанию не входит в safe reachable.

## 4. Размер и процедурные катакомбы

Начальный профиль для **1–2 игроков**: domain disk R=8 (217 клеток), внешний пояс — камень/граница; внутренний R=7 даёт 169 кандидатов. Цель после вырезания комнат/коридоров — 130–140 связанных traversable клеток, сопоставимо с 132/136 из square fixtures. Это предложение, а не механическая замена 15×15: диаметр по шагам и степень 6 меняют контакты и LOS.

Для **4 игроков** исходная база 24×24 имеет 384 проходимых fixture-клетки. Начальный кандидат — domain R=13 (547), внутренний R=12 (469), целевые 375–390 проходимых; выбрать окончательно после сравнения graph distances. Для 3 и более, включая 2×2/3×3/5×5, вычислять target playable budget из профиля режима, выбирать минимальный R с достаточным внутренним budget и запасом на стены. Не возвращаться к (6N)² без проверки времени матча и payload. До утверждения профилей создавать HEX для неизвестного размера режима запрещено с понятной конфигурационной ошибкой.

Процесс генерации:

1. Локальный PRNG(seed), фиксированный generatorVersion/config/catalogVersion; порядок обхода и выборок детерминирован. Не пользоваться глобальным rand/time. Сохранять seed и полную материализованную карту: один seed не восстанавливает runtime изменения.
2. Сформировать область камня и размещать комнаты как группы HEX по нескольким шаблонам: округлые, вытянутые по трём HEX-осям, небольшие ниши. Не делать все помещения идеальными шестиугольниками.
3. Построить граф комнат, соединить MST с ограниченным числом дополнительных связей. Проложить коридоры A* по carve cost; ширина обычно 1, выборочно 2 для обхода/контакта. Тупики оставлять как loot niches, не единственный обязательный маршрут.
4. Вывести edge walls из carved topology; внутренние перегородки/двери добавлять только с последующей проверкой графа. Нижняя граница стены всегда совпадает с blocked edge. Decorative columns размещать только в уже заблокированных клетках, никогда не сужать серверный проход визуально.
5. BFS/Dijkstra по финальным movement edges подтвердить одну компоненту всех обязательных playable клеток. Удалить необязательные изолированные карманы из playable или соединить; не размещать там объекты.
6. Разместить команды по **graph distance**, а не по координатной близости. Начальные пороги для прототипа: противники ≥6 шагов, до портала 5–12, разброс минимальных расстояний команд до портала ≤2; союзники в одной комнате на 1–3 шагах. Это параметры для согласования/seed sweep, не подтверждённый баланс. При нехватке ёмкости — новая bounded попытка, затем явная ошибка; не молча ослаблять пороги.
7. Поставить портал на свободном доступном floor, исключить spawn/portal overlap; разместить монстров, бочки и ресурсы после топологии. Начальная monster density близка .05 и loot density близка текущим условным вероятностям, но комнаты/коридоры получают отдельные лимиты. Не блокировать все выходы стартовой комнаты монстрами; оставлять маршрут, не требующий недостижимого боя.
8. Квестовый артефакт сейчас получается через логику бочек, а не обязательно лежит на карте. Проверить наличие хотя бы одной доступной подходящей бочки и сохранение fallback последней бочки в `handlers/barrel.go`; перенос в отдельную комнату — только как отдельное игровое решение.
9. Валидировать occupancy uniqueness, все objectives/rewards/exit, визуальные edge данные, min/max distance, долю floor, длину/плотность corridor. Ограничить количество попыток и логировать seed/config без пользовательских данных.

Измерять не только число floor: распределения spawn→portal, spawn→spawn, degree/corridor chokepoints, число путей, первый контакт, время добычи артефакта, время полного PvE/PvP. Seed sweep: минимум 1000 seed на профиль в будущем CI, 10 000 перед релизом; ошибка должна давать воспроизводимый seed.

## 5. Два клика: общая машина состояний

Один controller для Classic/3D/minimap overlays, живущий выше переключателя режима. Рендеры отправляют `hoverCell`, `selectCell`, `selectActor`, `cancel`, а не напрямую `fightMonster`/`movePlayer`. Удалить обход через `GameController.handleMapPlayerClick` и auto-action из directional path при включённом новом UX.

Состояния: `idle → movePreview | attackPreview → submitting → idle`, плюс `stale/rejected`. Preview содержит `{instanceId,geometryVersion,mapRevision,viewRevision,actorPosition,turnToken,target,path,cost,knowledgeClass}`. Только **последующий отдельный клик** той же цели при актуальном preview подтверждает. Не browser dblclick: задержка между двумя выборами не лимитируется, double event не должен вызвать два запроса.

Первый клик считает маршрут на клиенте по **разрешённому knowledge snapshot**, показывает шаги, общую энергию, доступный префикс и штрихованный остаток. Не отправляет mutation или скрытый server path query. Для известного препятствия — конкретная причина; unknown — «область не разведана», без обращения к скрытой occupancy. По умолчанию не планировать через unknown. По explored floor можно показывать оценочный путь с пунктиром, поскольку текущая занятость неизвестна; подтверждение ограничено безопасным видимым префиксом. Глобальная «оптимальность» обещается только в известном графе.

Второй клик подтверждает только уже показанный доступный префикс; на конце префикса рисуется маркер остановки. Если original target дальше бюджета, подпись «Подтвердить N шагов до …», остаток никогда не исполняется автоматически в следующем ходу. При полном отсутствии допустимого префикса подтверждение disabled.

Escape/правый клик отменяет preview; другой HEX заменяет. Hover не меняет выбранную цель. Touch: первый tap выбирает, второй tap либо явная кнопка «Подтвердить»; hover не нужен. Панорамирование/drag не считается кликом, контекстное меню подавляется только внутри игровой сцены. Клавиатура: шесть кнопок, например E/D/Z/A/Q/W с явно отображёнными направлениями (привязка по `KeyboardEvent.code` обсуждается отдельно); во вводе текста и модальных окнах обработчик выключен. Нужен один listener: `NachaloScene3D` сейчас имеет собственную обработку стрелок, а GameController использует `useGameKeyboard`. Выбор cell с клавиатуры и Enter идут через ту же preview/confirm машину.

При смене активного игрока, позиции, энергии, видимости, target ID/position, карты, отключении, смерти или финале preview отменяется/пересчитывается и требует нового подтверждения. При переключении Classic↔3D сохранять только актуальный preview; никаких повторных команд.

### Предлагаемый серверный протокол движения

Новый endpoint, **предлагаемый**, а не существующий: `POST /game/matches/{instanceId}/route`.

```json
{
  "commandId": "client-generated-unique-id",
  "geometryVersion": 1,
  "mapRevision": 1,
  "expectedStateRevision": 42,
  "turnToken": "opaque-active-turn-id",
  "from": { "q": 0, "r": 0 },
  "path": [{ "q": 1, "r": 0 }, { "q": 2, "r": 0 }],
  "maxEnergyCost": 6
}
```

JWT определяет actor; никакого доверия user_id из body. Path не включает origin, имеет bounded длину и не содержит повторов. Сервер не заменяет маршрут на скрытый более короткий: он валидирует предложенную последовательность и пересчитывает цену по настоящему состоянию. Клиент считает preview; сервер считает окончательные step costs и при необходимости свой A* только для внутренних задач, не раскрывая hidden graph. При равной цене клиент/сервер могут иметь общие алгоритмы, но присланный path остаётся недоверенным.

Проверка до исполнения: участие/живой/active, версия, turn token (не один TurnNumber: круг включает несколько ходов), revision, origin, rate/length limit. Под единой **очередью команд матча** или match lock сериализовать route, attack, endTurn/timer, сбор, postройки, push, disconnect death и финал. Одного `lockPlayer` недостаточно. Для нескольких экземпляров сервиса — DB row lock/CAS на matches или единый владелец матча; in-memory mutex обеспечивает только один процесс. Определить порядок lock и исключить nested захват старого `lockPlayer`.

Маршрут — одна принятая команда с последовательным исполнением шагов, **не обязательная all-or-nothing транзакция всего пути**. Каждый шаг атомарен в DB: проверить исходную позицию/edge/occupancy/energy, списать точную цену, обновить player+cell flags+artifact/aura state, увеличить revision, commit; затем publish через transactional outbox либо другой механизм гарантированного порядка. На новую видимость, изменившую доступность/цену/цели, damage, исчерпание энергии, deadline, block, смерть, завершение матча — остановить остаток. Для первой версии остановка при любом расширении видимости делает движение осторожным, но предотвращает неожиданный контакт. Будущий режим продолжения — отдельное решение.

Не выполнять auto-attack, auto-collect, auto-openBarrel и auto-extract внутри route. Если клетка содержит видимый ресурс/бочку, можно дойти до неё и остановиться для отдельного подтверждённого взаимодействия. Это намеренно меняет текущую клиентскую цепочку move→collect/open и требует согласования. End-turn timer ставит событие в ту же очередь, но executor проверяет deadline между шагами: очередь не должна позволять продлить ход длинным путём.

Ответ включает `commandId`, status=`completed|stopped|rejected`, подтверждённые segments/цены, final actor state, revision, видимый diff. Повтор commandId+тот же body возвращает сохранённый результат, другой body → conflict. После reconnect команда не возобновляется; клиент получает snapshot и может запросить outcome прежнего commandId. Для таймаута HTTP не повторять mutation новым ID.

Причина остановки не должна раскрывать невидимого unit/ауру. До появления информации в разрешённом view ответ общий «маршрут изменился». Точная энергия/HP самого игрока остаётся видимой ему как результат действия; preview не должен давать точные hidden-dependent costs. Отдельное решение: какие игровые последствия неизвестной ауры сами считаются допустимым раскрытием.

Анимация читает только confirmed segments. Если сервер прислал несколько шагов, поставить их в очередь, не интерполировать напрямую от origin к конечной клетке через стены. Redux хранит авторитетное состояние отдельно от display position; новый snapshot отменяет старую visual queue. Длительность = projected world length/speed, не длина axial вектора.

## 6. Атака и общие состояния подсветки

`CanAttack`: свой живой actor, активный ход, видимая живая вражеская цель того же матча, корректный team rule, достаточно энергии с артефактами, HEX range, LOS, применимые class rules. Melee — сосед D=1 и незаблокированное attack edge; D=0 не допускается нормальной occupancy. Ranged Ranger D=2 по текущему шаблону, Mystic D<=3, при D=1 остаётся текущий melee mode/counter policy. Не превращать все атаки Mystic в режим без LOS автоматически; magic — presentation style, а не существующее разрешение стрелять через стены.

Первый клик видимого врага → `attackPreview`, красный target outline, линия выстрела/блокирующее известное ребро, стоимость. Второй клик **по тому же actor ID**, при прежней позиции и актуальном turn/view revision → attack command с commandId/versions/expected revision/target ID. Одинаковый HEX с новым врагом не тот же target. Сервер заново проверяет CanAttack и выполняет весь существующий exchange (primary/counter/fury/drain/push/death); RNG/proc не показывать как гарантированный результат.

Ranger push: выбрать из шести направлений то, чей нормализованный world-вектор имеет максимальный dot с направлением attacker→target, tie — меньший i. Destination=target+dirs[i]; блокируется edge/terrain/structure/unit/boundary. Это правило отличается от sign(dx),sign(dy) и должно пройти отдельные tests третьего попадания/fallback/refund. Aura radius=2 становится HEX disk (19 клеток вместо Manhattan diamond 13); даже сохранённые цифры меняют баланс.

| Состояние | Общее отображение Classic/3D | Когда допустимо |
|---|---|---|
| unknown | Непрозрачный fog, без affordances | Нет разрешённых данных |
| explored | Приглушённый статический terrain | Только сохранённое знание без dynamic entities |
| hover / selected | Тонкий белый / яркий контур | Только разрешённый cell |
| reachable | Синий контур, energy tooltip | Видимый допустимый граф текущего хода |
| routeAffordable | Сплошная линия, номера шагов | Подтверждаемый префикс |
| routeRemainder / uncertain | Пунктир/штриховка, маркер остановки | Дальше энергии либо по explored terrain |
| blockedKnown | Оранжевая граница + текст | Известная стена/occupied/structure |
| attackable / attackSelected | Красный outline / линия + confirm | Только видимая цель с CanAttack |
| visibleUnattackable | Приглушённый marker + причина | Только видимый враг: range/LOS/energy |
| pending / stale | Спиннер / серая отменённая линия | Команда в полёте / snapshot изменился |

Цвет дублируется формой/штриховкой/текстом. Нельзя красить unknown клетку в blocked из-за скрытого монстра, делать tooltip с его ID либо показывать дальность скрытого противника. Красная подсветка не гарантирует урон, только допустимость попытки атаки.

## 7. Секретность и авторитетность

Заменить builder полного состояния для клиентов на viewer projection, вызываемую GET, JOIN/reconnect, WS patch, combat/drop/quest/portal/log events и HTTP mutation responses. Внутренний полный builder может остаться серверным. Членство матча проверяется перед выдачей snapshot и подпиской; dead/spectator policy определяется явно. В `UniversalAttackHandler` внешние команды принимаются только от игрока, вызов monster attack — внутренний серверный путь.

Server FOV строится по HEX radius+LOS и объединяется только для одной ненулевой группы; FFA с group=0 не команда. Exploration желательно хранить на сервере на команду/игрока для reconnect; sessionStorage — cache с geometry/mapRevision, не источник прав. При потере видимости отправлять removal/redaction unit, не оставлять старого врага в Redux. Explored terrain хранить как last-seen, не незаметно обновлять скрытые двери/постройки. Новая wall topology передаётся только когда известна.

До recipient filtering нельзя включать строгую HEX-подсветку и обещать отсутствие утечек. `adaptRealMap` — дополнительная защита отображения, не граница доступа. Разведсвиток — отдельный разрешённый limited disclosure: одна координата q/r, никаких невидимых actor payload. Глобальные квестовые/портальные объявления должны либо не содержать скрытой позиции, либо быть явным игровым исключением.

## 8. Читаемость 3D: решения для будущей реализации

Сейчас ортографическая камера offset=(7,12,9), стены ~1.9 world height, fading до .2, occlusion sampler пять лучей по silhouette; уменьшение opacity не меняет LOS. Ни камера, ни материалы этим заданием не меняются.

| Решение и место будущей правки | Польза | Проблема/ограничение | Сложность |
|---|---|---|---|
| HEX outlines пола в `NachaloScene3D` | Читается клетка и маршрут | Z-fighting/шум; batched lines, только known | С |
| Шесть выходных маркеров и blocked-edge colors | Видно разрешённый переход | Не подкрашивать hidden occupancy; цвета + форма | С |
| Постоянное кольцо героя + world/screen marker | Не теряется собственный герой | Не накрывать цель клика, pointerEvents none | Н |
| Route overlay выше стен / отдельный pass | Путь виден при перекрытии | Только known path; depthTest=false не для скрытых объектов | С |
| Cutaway верхней части перекрывающих edge walls | Сохраняет проходы и обзор | Нужны cap/согласованные shadows и picking | В |
| Силуэты героя и **видимых** врагов | Видна цель за мешающей камерной стеной | Нельзя рисовать enemy silhouette вне server FOV | С–В |
| Постоянный нижний контур стены | Понятна коллизия при cutaway | Согласовать толщину и порядок overlays | С |
| Поворот камеры шагами 60° + zoom bounds | Можно осмотреть комнаты | Пересчитать input mapping, billboards, occlusion, NDC picking | С–В |
| Снижение wall height / гибрид cutaway | Меньше перекрытия по умолчанию | Потеря масштаба/атмосферы; сравнить на fixture rooms | С |
| Визуальные перепады пола / ступени | Читаемость зон | Настоящие уровни требуют height/LOS/path rules; пока только декор | В для gameplay |

Приоритет: outlines/edges/route/player marker → lower wall contour и cutaway → поворот/zoom → художественная настройка. Occlusion должен работать с edge meshes и стабильными cell IDs, только видимыми разрешёнными targets. Sprite objects, Ranger cues, light/torch transforms, projectile, hit, death, cameraFocus проходят общую hexToWorld; изменение GLB/Blender для этого не требуется.
