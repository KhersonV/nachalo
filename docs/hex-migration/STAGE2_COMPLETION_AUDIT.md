# Stage 2 completion audit — 19 October 2026

## Scope and verdict

This is an audit of the current working tree on `feat/shop_improovement`, including its uncommitted combat changes. It changes no executable code or SQL. The reference contract is `MIGRATION_PLAN.md`, `STAGE2_NOTES.md`, `stage1_geometry.sql`, and `stage2_commands.sql`. The checks below trace actual HTTP, timer, WebSocket, repository, game-state, and client call paths. They do **not** infer atomicity merely from an advisory lock or from a compiling test.

**Stage 2 is incomplete.** A subset of movement, collection, and combat uses `MatchCommand`, but turn processing, portal finalization, barrel, inventory use, scrolls, building, and disconnect death can still write a live match through independent commits. `combat_results_complete` is never set true by production code, so `FinalizeMatchTx` cannot yet replace `FinishMatchHandler` for a real match. No migration was applied to any database for this audit.

The `TURN_PASSED` portion of R19 is complete: emitters provide `active_user` alongside legacy `userId`, and the Redux handler accepts either field while rejecting a missing player ID. These conclusions are backed by isolated-PostgreSQL schema and HTTP replay tests, the new Node turn contract, full Go tests, existing Node tests, `tsc`, and production build. R18 and R19 remain open for the other callers and patch `PLAYER_DEFEATED` behavior. No change was made to the other audit tasks.

**B01 update, 19 October 2026:** B01 is complete. `DamageEvent` and `KillEvent` now carry `sourceType` (`player`, `monster`, or `environment` for non-actor damage). Every current combat-result producer supplies the type, and transactional append rejects an untyped new event. The reward calculator credits outgoing damage/kills only when `sourceType=player`; damage *received* by a player still counts regardless of source. Old JSON without `sourceType` remains readable and is treated as **unknown**, so its outgoing events are never attributed by matching a numeric ID. No automatic guessing or rewriting of old rows occurs; their `combat_results_complete=false` remains unchanged pending B02's verified history policy. PvP/PvE, both lethal directions, replay, rollback and reward equality after `RestoreMatchStates` passed on an isolated PostgreSQL with player ID 1 = monster ID 1. The existing XP/coin/placement formulas are unchanged.

Legend in the tables: **MC** = one `MatchCommand` / match row lock / `sql.Tx`; **A** = session advisory match lock but independent database writes; **none** = neither; **conditional** = only the listed branch. “Revision” means both the durable revision and a client-visible revision-bearing event where relevant. ## Result history, recovery and finalization blockers

`game/results.go` uses `DamageEvents`, `KillEvents`, and `DefeatedUsers` to calculate existing XP/results. Supported MC combat branches append these to `matches.combat_result_events` in the same Tx, and `RestoreMatchStates` can reload them for unfinished matches. Legacy combat, turret, barrel, disconnect and some class branches update only `MatchState` or write independently. Quest artifact/resource ownership belongs in existing match inventory/cell tables, not automatically in the combat-event JSON. Their persistence still matters to who can evacuate and what gets synchronized at finalization. `MatchState` also holds turn-scoped class effects, Guardian pressure, Boots movement count, consumable cooldown, turn timers/deadlines and disconnect grace that are not fully restorable. `RestoreMatchStates` reloads turn order/turn number/active user and persisted result events, but does not recover these operational states or reschedule timers.

The event model now distinguishes `sourceType` from numeric `DealerID` / `KillerID`, so a monster instance ID colliding with a user ID is not credited to that user. Untyped historical events remain ambiguous and conservatively uncredited for outgoing damage/kills; player damage taken remains readable. Death order must be appended once per defeated user, including counterattack, aura, turret, barrel and disconnect. A match created before complete event capture cannot be declared complete merely by backfilling `combat_results_complete=true`; it needs verified event reconstruction or must finish through a deliberately retained legacy cohort policy. **Production code currently never sets this flag true.** The SQL default `false` is appropriate.

`FinalizeMatchTx` already guards `finished_at`, checks completeness, saves results/profile rewards in one Tx and can be called inside an existing `MatchCommand`. Its standalone wrapper is not a substitute for joining the portal/death operation: doing so after a separate winner write reopens the same split. The legacy `service.FinalizeMatch` deletes `matches`; `match_commands` has `ON DELETE CASCADE`, so deletion also destroys replay evidence. Retain finished rows/ledger until a separate retention policy safely archives them.

### Exact cutover sequence for `FinishMatchHandler`

1. Deploy/verify Stage 1 then Stage 2 schema on an **isolated test DB** and add production schema readiness checks for revisions, ledger, result JSON, completeness and `finished_at`. Roll out schema before routing new commands; this audit applies no migration.
2. Complete every result-event producer and restart recovery below. Add typed actor attribution and tests proving the old formulas give the same result before/after restart. Mark `combat_results_complete=true` **only** for a proven full-history cohort, within the match lifecycle; leave old/incomplete matches false and plan their drain/reconciliation explicitly.
3. Move portal authorization and the **currently enforced** artifact/winner checks into a new `MatchCommand` begun by `FinishMatchHandler`. Keep a single canonical payload and `commandId`, reject a different payload with the same ID, check `finished_at`/active match under lock. Do not silently add a new portal-position rule during this migration.
4. In that same Tx, write `winner_id` / `winner_group_id`, apply any evacuation-related inventory/quest-artifact/result event, call `FinalizeMatchTx`, and save the ledger response plus exactly one state revision (map revision only if a cell actually changes). On any error, roll back winner, stats, XP, inventory, finished marker and ledger together. Do not call `SetMatchWinner` or `service.FinalizeMatch` on this path.
5. Commit first. Only then update/remove in-memory state, stop timers and emit one authoritative revisioned `MATCH_PATCH` plus compatible `PLAYER_LEFT_PORTAL` / match-finished notifications carrying the same `commandId`. Legacy copies must be ignored by revision-aware clients. A replay should return the committed response without a second reward or notification.
6. Join `FinalizeMatchTx` to the **same** `MatchCommand` when player death ends a match, after HP, queue, artifact, placement and result events have been written. No nested transaction or second lock. Finish without deleting match/ledger; define asynchronous cleanup after the replay-retention interval.
7. Gate traffic/cutover by cohort completeness. Test real HTTP portal and last-player-death success, concurrent portal/death, duplicate/conflicting IDs, reward-write failure rollback, crash/restart replay, old incomplete cohort behavior, and WS silence until commit. Compare rewards with the legacy formulas for solo/team cases before enabling the route.

The sequence is blocked today by incomplete event sources, memory-only turn/effect state, split portal/death flows, and old-match history. A flag flip or a direct call to the standalone finalizer would not be safe.

## WebSocket, revisions and multi-process behavior

`MATCH_PATCH` carries revisions; `useGameSocket.ts`/`revisionGate.mjs` rejects duplicate or older patches and requests a snapshot on a gap. Legacy copies with `commandId` are ignored by this client, avoiding duplicate Redux application for migrated commands. `COMBAT_EXCHANGE` within a patch reaches `createWsHandlers`, and HP updates are applied once. **Fixed in this update:** `TURN_PASSED` now supplies `active_user` and `userId`, and the Redux handler normalizes both, so a patch cannot overwrite the active player with `undefined` from a missing field. The patch dispatch path still bypasses `useGameSocket`'s special `PLAYER_DEFEATED` handling (session cleanup/socket close). Legacy, nonrevisioned events remain vulnerable to duplication/out-of-order delivery.

On reconnect, WS `JOIN_MATCH` and HTTP snapshot load the latest state, but `BuildMatchResponse` reads match/players/map separately and may return a mixed snapshot. Put those reads in a consistent read transaction tied to the returned revisions; remove the write-on-read quest-artifact backfill. **Fixed in this update:** `SchemaReady` checks Stage 1/2 tables and columns, and startup refuses to start match runtime when they are missing.

PostgreSQL locking serializes commits, **not** event delivery among Go processes: commit A can precede B while B's WS patch reaches a client first. Revision gap detection should cause snapshot resync, not a claim of globally ordered delivery. In-process WS clients are not shared across backends, and there is no durable outbox or cross-process fanout; a process dying after commit but before broadcast can lose the event until reconnect or a later revision gap. Concurrent goroutines also write to client sockets without an evident per-client serialized writer. Durable outbox/fanout is required before multi-backend guarantees; single-backend operation still needs restart/reconnect recovery and consistent snapshots.

## Durable-data risks

Independent commits can charge energy/item without applying damage/effect, save winner without reward, reward without complete statistics, or emit success before rollback. `service.FinalizeMatch` can remove the match and command ledger while a client retries, allowing unprovable reward history. Lost memory-only effects after restart can change damage, movement cost, cooldown, turn timing or result placement. Direct `BuildMatchResponse` backfill mutates a match outside its revision history. An incomplete or misattributed `combat_result_events` history changes permanent XP/rewards. Schema presence is now checked before runtime; it does not prove completeness of historical event data or successful content backfills. Preserve existing user DB/volumes; test migrations and failure injection only on isolated copies.
