# Этап 1: контракт и применение схемы

`square-v1`: `schemaVersion: 1`, `geometry: {kind:"square",coordinates:"cartesian",version:1}`. Старые строки без metadata читаются именно так. Позиции игроков, монстров и клеток остаются в `x/y`; старты и портал остаются массивами `[x,y]`. `cell_id` остаётся построчным только для квадратной карты.

`hex-v1`: `schemaVersion: 2`, `geometry: {kind:"hex",coordinates:"axial",orientation:"pointy",version:1}`. Позиции — отдельные `q/r`, включая отрицательные значения и `(0,0)`. Стартовые позиции и портал в будущих записях хранятся в `start_positions_v2` и `portal_position_v2` как JSON с объектами `{q,r}`. У клеток отдельные `q/r` и независимый стабильный `cell_id` (его назначение входит в этап 4). Стены между клетками — `match_hex_edges`: направление 0 ведёт к `(q+1,r)`, 1 — к `(q+1,r-1)`, 2 — к `(q,r-1)`. Внешние ключи требуют наличия обеих клеток. Существующий runtime пока отклоняет HEX snapshot; создание HEX отключено.

Старые тестовые square-матчи временно поддерживаются. При фактическом переходе на HEX их можно удалить отдельным разрешённым действием и начать с чистых HEX-матчей. Аккаунты, персонажи, инвентарь, экипировка и прогресс сохраняются. Пересчёт `x/y` в `q/r` не предусмотрен.

Миграция [stage1_geometry.sql](stage1_geometry.sql) выполняется **вручную, один раз**, после существующего `RunMigrations`. Отдельный маркер `hex_stage1_migration_marker` гарантирует, что повторное применение сразу завершится ошибкой duplicate key, без частичного изменения схемы. `RunMigrations` вызывается при старте backend, поэтому не следует запускать backend против пользовательской БД только ради этой миграции. Перед применением к нужной БД проверьте её копию и отсутствие `NULL` в legacy `match_players.position`, `match_map_cells.x/y`, `match_monsters.pos_x/pos_y`. Скрипт не преобразует координаты и не удаляет данные.

Миграция проверена 19 октября 2026 на новом локальном PostgreSQL 14: штатный `RunMigrations`, первое применение SQL, вставка и чтение square-матча через repository и `BuildMatchResponse`, вставка HEX `q/r`, игроков, монстров и рёбер через SQL, отказы для смешанных/повторных координат, неверного направления, отсутствующего соседа и неизвестной версии. Повторное применение завершилось ожидаемой ошибкой маркера. На пользовательской БД миграция не запускалась. Полный игровой E2E и HEX runtime не проверялись.

Счётчики `map_revision` и `state_revision` подготовлены со значением 0; их атомарное увеличение, порядок patch-событий, typed command patches и надёжное восстановление входят в этап 2. Существующие `UPDATE_CELL`, `MOVE_PLAYER`, `COMBAT_EXCHANGE` остаются квадратными; клиент проверяет координаты входящих patch-событий и отбрасывает несовместимые. Для будущего HEX-пути понадобятся отдельные repository readers/writers, валидаторы полноты HEX-карты и snapshot, а также правила этапов 4–8.
